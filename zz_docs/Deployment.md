# Deployment

Moved out of [CLAUDE.md](../CLAUDE.md) to keep that file light for day-to-day coding work — this content is only relevant when actually touching deployment/infra, not while writing feature code. See CLAUDE.md's own "(see Deployment)" cross-references, which point here.

- **Server**: Infomaniak VPS Lite (Ubuntu 22.04), `179.237.86.113`, no domain purchased. SSH as `ubuntu` (key-based, passwordless `sudo`) — see [Decisions.md](Decisions.md) for why Infomaniak/a VM over a PaaS, and Nginx over Caddy.
- **Two firewalls needed**: OS `ufw` (22/80/443 only) *and* Infomaniak's own Cloud panel firewall (80/443 had to be opened there too).
- Repo cloned at `~/docky`, updated via `git pull`, auth via a read-only deploy key (`~/.ssh/docky_deploy_key`) for manual pulls, a separate dedicated key for CI (see below) - neither is a personal key.
- **`docker-compose.prod.yml`** (not the dev one) runs prod: `nginx` is the only service publishing ports (80 and 443), routing `/api/*` to `backend:3000` (prefix stripped in `nginx/nginx.conf`) and everything else to the built Angular app (own SPA fallback in `frontend/nginx.conf`) — hence `environment.prod.ts`'s relative `apiUrl: '/api'`. Uploads go to a named volume (`backend_uploads`), not the dev bind mount. **If only an nginx config changed** (no code), `up --build -d` won't make the running container reread it — `docker compose -f docker-compose.prod.yml restart nginx` after.
- Real prod secrets live in `.env`/`backend/.env` *on the server only*, never committed.
- **HTTPS via [sslip.io](https://sslip.io) + Let's Encrypt**: no domain bought, so `179-237-86-113.sslip.io` (resolves to the server's own IP, free, no signup) stands in for one - Let's Encrypt won't certify a bare IP but will certify that. `certbot` (installed via `apt` on the host, not containerized) obtains/renews the cert with the `webroot` method: nginx serves `/.well-known/acme-challenge/` from `/var/www/certbot` (a host path bind-mounted into the nginx container, both `:80` and the cert's own `/etc/letsencrypt` — see `docker-compose.prod.yml`), so renewal never needs nginx to stop. Port 80 otherwise 301-redirects to 443. Renewal is certbot's own systemd timer; its config (`/etc/letsencrypt/renewal/179-237-86-113.sslip.io.conf`) has a `renew_hook` that restarts the `nginx` container so it picks up the renewed cert. **Gotcha hit once**: that `renew_hook` line has to sit in the flat `[renewalparams]` key/value area, *before* the nested `[[webroot_map]]` table - appended after it, certbot silently mis-parses it as a webroot-map entry instead and every renewal fails. Verify with `sudo certbot renew --dry-run` after touching this file (takes several minutes non-interactively - certbot adds its own randomized delay, that's normal, not a hang).
- **CI/CD**: `.github/workflows/deploy.yml` - on every push to `main` (or manual `workflow_dispatch`), two jobs run in parallel (`tsc --noEmit` + `npm test` on both sides, the backend's integration tests too - `npm run test:integration`, its own throwaway Postgres through Docker, already on the runner - and `ng build` on the frontend); a third job only runs if both pass, and SSHes in to run the exact manual redeploy command below. Uses `appleboy/ssh-action`, authenticating with a dedicated ed25519 keypair (`github-actions-docky-deploy`, added to the server's `authorized_keys`) stored as the `DEPLOY_SSH_KEY`/`DEPLOY_HOST`/`DEPLOY_USER` repo secrets - not a personal key. Builds still happen on the VPS itself (`docker compose ... --build`), no image registry involved - revisit if the VPS ever struggles with that build load.
- **Redeploy** (automatic on push to `main` via CI above; this is the same command for a manual one): SSH in, `cd ~/docky && git pull && docker compose -f docker-compose.prod.yml up --build -d`.
- **Weekly demo reset**: the demo company (company 2, Rénov Alpes - see CLAUDE.md's Backend "Seed data" bullet) is reset every Sunday 02:00 by a cron job in the `ubuntu` user's own crontab on the server (`crontab -e`, not versioned here - same as the rest of the server-side config, e.g. certbot's renewal timer): `0 2 * * 0 /home/ubuntu/docky/scripts/reset-demo-cron.sh`. That script runs [scripts/reset-demo-company.sql](../scripts/reset-demo-company.sql) inside the running `postgres` container (`docker exec`, single transaction) - it deletes everything company 2 owns and re-inserts the exact same rows `001_data.sql` created for it, using the same explicit ids and `CURRENT_DATE`-relative dates, so the chantiers/invoices re-center on "today" again. Company 2's own `companies` row and its users' `language` are put back to their seed values too (a visitor can edit the company's name/IBAN/logo), but the rows themselves are kept (login stays stable). Then it purges company 2's files from MinIO (`companies/2/` - logo, header image, project attachments) via `node dist/shared/storage/purge-company-files.js 2` inside the backend container. Never touches company 1, and isn't a `docker compose down -v` (no downtime, no effect on company 1). To change the frequency, edit that one crontab line's schedule expression - e.g. `0 2 * * 0,3` for twice a week (Sunday and Wednesday).
- **Nightly database backup** - [scripts/backup-db.sh](../scripts/backup-db.sh), run at 03:30 by the `ubuntu` user's crontab (same place as the demo reset, not versioned). **Install** (once): `mkdir -m 700 ~/docky-backups` first - cron opens the log before the script runs, so a missing folder would fail silently every night - then `crontab -e`: `30 3 * * * flock -n /tmp/docky-backup.lock /home/ubuntu/docky/scripts/backup-db.sh >> /home/ubuntu/docky-backups/backup.log 2>&1` (`flock`: a manual run never overlaps the nightly one). **What it does**: dumps the live database (`pg_dump -Fc`, one consistent snapshot even mid-save) to `~/docky-backups/docky-YYYY-MM-DD.dump` (outside the repo and every container, readable by `ubuntu` only - `umask 077`), restores it into a scratch database `<db>_incoming` of the separate `postgres-backup` service (`docker-compose.prod.yml`: own volume, no network at all, only reached through `docker exec`), checks it (every live migration, at least one company), and only then swaps it in as `<db>` - so every kept dump is known to restore, a broken one never wipes the last good copy, and yesterday's data can be read without touching the live database (`docker exec -it docky-postgres-backup psql -U <user> <db>`). A dump that fails to restore or check is renamed `.unverified`. About 14 days of dumps are kept. Any failing step posts to the errors Discord channel (`DISCORD_WEBHOOK_URL` from `backend/.env`, only the step name); a success is only logged (`~/docky-backups/backup.log`).
  **To restore the live database from a dump** (in `~/docky`, with the dump's date):
  1. `docker compose -f docker-compose.prod.yml stop backend`
  2. `docker exec docky-postgres sh -c 'dropdb -U "$POSTGRES_USER" --force "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'`
  3. `docker exec -i docky-postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --exit-on-error' < ~/docky-backups/docky-YYYY-MM-DD.dump` - into an empty database, not `--clean` over the current one (a table created after the dump would block it and leave a mix of both days)
  4. `docker exec docky-postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "DELETE FROM refresh_tokens"'` - sessions revoked since the dump would otherwise come back; everyone logs in again
  5. `docker compose -f docker-compose.prod.yml start backend` - it re-applies any migration newer than the dump
  6. `scripts/reset-demo-cron.sh` - the demo company's files may have been purged since the dump
  Copies, not a live replica - a mistake only reaches the next night's copy - but on the same VPS: losing the server loses them too (an off-server copy is still to decide), and a backup that stops running (crontab lost) raises nothing. MinIO files (logos, attachments) aren't backed up yet. Deleted data stays in the dumps for up to 14 days.
- **Uptime monitoring**: an external monitor ([UptimeRobot](https://uptimerobot.com), free plan, configured in its own dashboard - not versioned here) calls `https://179-237-86-113.sslip.io/api/health` every 5 minutes and alerts by email when it fails. `GET /health` (`backend/src/modules/health`, public, no token) answers 200 `{ status, database, storage }` only once the database (`SELECT 1`) and MinIO (`HeadBucket`) both answer within 3s each, 503 otherwise - so a backend that runs but can't reach its database still alerts. A second monitor on the site's own root covers nginx/the frontend, and UptimeRobot also warns before the HTTPS certificate expires.
- **Errors**: recorded and grouped in our own database, read at `/settings/errors` (see CLAUDE.md's "Error tracking" bullet). A new or returning one is announced in a private Discord channel through its webhook: `DISCORD_WEBHOOK_URL` and `APP_URL` (`https://179-237-86-113.sslip.io`, for the link) in the server's `backend/.env`, picked up on the next backend restart/redeploy. The message never holds the error's own text - the details stay on our server. The backend's production image runs `node --enable-source-maps` (`tsconfig.json`'s `sourceMap`), so a recorded stack points at the TypeScript lines, not the compiled ones.
- **Known gaps**: no real domain (by choice, see [Decisions.md](Decisions.md)); no Content-Security-Policy header yet (see CLAUDE.md's Known gaps). The refresh-token cookie is `Secure` in prod through `COOKIE_SECURE=true` in the server's `backend/.env`, and nginx sends HSTS - **an `nginx/nginx.conf` change needs `docker compose -f docker-compose.prod.yml restart nginx` after the redeploy**, CI's `up --build` doesn't make nginx reread it.
