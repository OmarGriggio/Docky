# Difficulties encountered

This file tracks concrete problems hit while building Docky and how they got diagnosed and fixed — as opposed to [Decisions.md](Decisions.md), which logs choices that had more than one reasonable option and the trade-off between them. A decision can be made calmly with all information in hand; a difficulty is something that broke, didn't scale, or turned out wrong only once real use (or real deployment) exposed it. Several entries here are the "what went wrong" half of a decision logged there — cross-linked both ways.

Organized by area, not by severity or date.

## Business & domain modeling

**Document numbering wasn't scoped per company.** `documents.number` started as a plain `UNIQUE` column — fine until noticing two companies both issuing `FAC-2026-0001` would collide, which is guaranteed to happen since the format resets every year. Fixed by scoping the constraint to `UNIQUE (company_id, number)` and generating the next sequence with `LIKE 'FAC-2026-%' ORDER BY number DESC LIMIT 1` scoped the same way, in `document.service.ts`'s `generateDocumentNumber`.

**A flat list of document lines couldn't express real sections.** First schema (2026-09-02) kept `document_lines` a single list ordered by `position`, with `SECTION`/`NOTE` added as two more `type` values acting as in-list markers — no join, matched how Odoo's own invoice lines work, and avoided the up-front cost of a `document_sections` table for a feature nobody had asked for yet. That held until the `document-form-v2` frontend prototype needed a subtotal per section: a `SECTION` marker line has no way to know where "its" lines end other than "everything up to the next `SECTION` line," which can only be answered by walking the whole list — there's no query that stops at a subtotal. Reopened and reversed (2026-09-09) into a real `document_sections` table with `document_lines.section_id NOT NULL`, `position` scoped per section instead of per document. See [Decisions.md](Decisions.md#invoicing-schema-gaps) for the final shape.

## Architecture & design

**"Closest to now" isn't something a plain aggregate can express.** The chantiers list needed to sort in-progress projects by whichever of their sections has a `date_start` closest to right now — in *either* direction, since an overdue section is just as urgent as an upcoming one. A first instinct reaches for `MIN(date_start)`, but `MIN` only answers "earliest overall," not "closest to now" — an overdue section from last month and one starting next week aren't ordered by proximity that way. Solved with a `LEFT JOIN LATERAL` that, per project, picks the single section minimizing `ABS(date_start - now())` — something a plain `GROUP BY` + aggregate has no way to express. `project.repository.ts`'s `getProjectsFromDB`.

**Letting a platform admin act on a company's data without widening every existing check.** Once cross-company impersonation existed, every endpoint that checked `role === 'ADMIN'` needed to also let a `PLATFORM_ADMIN` through — easy to add, easy to forget one spot, and each forgotten spot is a silent feature gap rather than a loud bug. Rather than widen every check (the pattern `company.routes.ts` already used for its own ownership checks), user management was moved entirely behind `PLATFORM_ADMIN` instead: `GET /user`, `DELETE /user/:id`, and the authenticated branch of `POST /user` stopped accepting a company's own `ADMIN` at all. One narrower rule beats the same widening applied N times. See [Decisions.md](Decisions.md#roles-company_id-stays-not-null-platform-admin-created-by-hand).

## Security

**Cross-tenant data leaks were the default, not the exception.** `company_id` is the tenant boundary in a multi-tenant schema, but nothing enforces it automatically — a repository function fetching one row by `WHERE id = $1` and forgetting `AND company_id = $2` compiles fine, passes a casual test, and quietly lets any authenticated user read or edit another company's client/project/document by guessing an id. An audit turned up this exact pattern in nearly every module (list endpoints were fine — they already filtered by `company_id` — single-resource ones mostly weren't). Fixed module by module; now a fixed rule for every new endpoint touching a resource by id (see `CLAUDE.md`'s Backend section).

**A public "register a company" endpoint doubled as a privilege-escalation path.** `POST /user` has to work unauthenticated (you can't be logged in before your account exists) and reuses the same route for an authenticated `PLATFORM_ADMIN` adding an employee — told apart inside `createUserService` by whether a valid token is present. The unauthenticated branch originally trusted whatever `company_id` was posted, which meant anyone could add themselves as `ADMIN` onto any existing company by guessing its id, not just create a new one. Fixed by only allowing that branch to succeed when the target company has zero users yet, so it can only bootstrap a brand-new company.

**Refresh-token storage started from convenience, not from the threat model.** First version kept the refresh token in `localStorage`, same as the access token — no CORS/cookie work needed while the CORS gap was still an open, deliberately-deferred item. That stopped being good enough once XSS mitigation mattered more than that convenience: anything that can run JS on the page can read `localStorage`, so a stolen refresh token there is a stolen 7-day session. Moved to an `httpOnly` cookie (frontend JS can never read it), landing on `SameSite=Lax` once it turned out every real deployment shape (`ng serve`'s dev proxy, nginx in prod) already puts frontend and backend on the same site, keeping the CSRF surface this reopens small. See [Decisions.md](Decisions.md#refresh-tokens-httponly-cookie--db-tracked-no-rotation-reactive-interceptor).

## Infrastructure & deployment

**Two firewalls, only one of them visible from the OS.** After configuring `ufw` and Nginx correctly, the VPS was still unreachable on 80/443 — because Infomaniak's Cloud panel has its own network-level firewall, independent of anything running on the box, defaulting to SSH-only. Nothing on the server itself hints that a second firewall exists; worth checking first on any cloud VM that looks correctly configured but won't answer.

**Free HTTPS without owning a domain, and a renewal that silently mis-parses.** Let's Encrypt won't certify a bare IP, solved with [sslip.io](https://sslip.io) resolving `<ip>.sslip.io` back to the server's own address for free. The harder part came later: certbot's renewal config needs a `renew_hook` to restart nginx after each renewal, and that line has to sit in the flat `[renewalparams]` section of `renewal/*.conf` — appended after the nested `[[webroot_map]]` table instead, certbot silently misreads it as a webroot-map entry and every renewal fails with no obvious error pointing at the real cause. Caught by testing with `certbot renew --dry-run` rather than trusting the file was fine because it looked fine.

**A pinned Docker image quietly stopped being pullable.** `docker-compose.yml` pinned `minio/minio:RELEASE.2025-09-07T16-13-09Z` — nothing in the repo changed, but a fresh environment's `docker compose up` started failing on `pull access denied`, including for `minio/minio:latest`. Confirmed it wasn't local (network, proxy, Docker Desktop config) by calling Docker Hub's own auth API directly with `curl`, bypassing Docker Desktop entirely: even a fully anonymous token request came back with an empty access list for that repository, meaning Docker Hub itself was refusing the pull for everyone, not just this machine — MinIO had cut public Docker Hub access to its own images. Fixed by pointing at the same image, same tag, on MinIO's other registry (`quay.io/minio/minio`), where it was still reachable. A second, unrelated issue then showed up right after (`SignatureDoesNotMatch` from MinIO) — traced to `backend/.env` still holding a `S3_SECRET_KEY=change_me` placeholder that had never been filled in to match `MINIO_ROOT_PASSWORD`, only surfacing once the container could actually start and reach MinIO for the first time.

**Adding a dependency and rebuilding doesn't always pick it up.** `docker compose up --build` alone can leave a stale `node_modules` after adding a backend package — the anonymous volume that exists specifically to stop the `./backend:/app` dev bind mount from shadowing installed dependencies persists across rebuilds, so a rebuild reuses the old one. `docker compose down -v` first forces a clean install (also drops `postgres_data`, harmless since migrations rerun on an empty volume).

## Frontend & performance

**The initial bundle grew past budget by loading the whole app eagerly.** Every route was originally `component:`-registered, so the first paint pulled in code for pages nobody had navigated to yet — 1.21 MB against Angular's 500 kB/1 MB budget. Fixed at the actual cause (switching every route to `loadComponent`) rather than the symptom (raising the budget), bringing the initial bundle to 485 kB.

**A sticky nav competed with page content purely by DOM order.** `nav-bar` uses `position: sticky`, which alone leaves `z-index` at `auto` — without an explicit value, the nav's whole subtree stacks against page content by source order alone, and no amount of `z-index` on a descendant tooltip fixes a stacking context the parent never established. Separately, making the expanded rail's items fill the available width needed both `min-w-0` and an explicit `md:w-full` on the same element — a flex item's default "never shrink below content size" floor left it a few pixels short even with the parent set to stretch. Both were only visible by testing at the actual breakpoint, not by reading the CSS.

## Process & methodology

**Starting tests on a codebase with none.** First tests ever written for this project — going straight to a full integration setup (a dedicated test database, Supertest against the whole Express stack) risked adding more moving parts than understanding gained on day one. Started instead with unit tests on pure functions only (no DB, no network, nothing async), deliberately covering a small fraction of the code, to build the habit before adding machinery. Real bugs found around that time (broken SQL inserts, an endpoint missing `authenticate`) were exactly the kind only an integration test would have caught — a known gap of this approach, not a blind spot in it.

**Renaming a live codebase's entire vocabulary, French to English.** Tables, columns, folders, routes and docs all carried French business terms alongside English technical code — moved to English everywhere except seed data and frontend UI text (both shown to a French-speaking end user, not code). Done in four phases (schema, backend, frontend, docs), each verified independently (fresh-Postgres checks, clean `tsc`, green tests, a full end-to-end pass including PDF generation) before starting the next — a repo-wide rename is exactly the kind of change where skipping verification between steps turns one typo into a debugging session with no idea which phase caused it.
