# Authentication, roles and permissions

Login, tokens, employee permissions, impersonation and user management. The rule of thumb - every role check is server-side, the UI only follows - stays in CLAUDE.md.

Moved out of CLAUDE.md on 2026-11-26 - keep it up to date in the same commit as the code it describes.

## Backend

- Auth: JWT (`jsonwebtoken` + `bcrypt`), guard in `shared/middlewares/auth.middleware.ts`. Rate limits (`shared/middlewares/rate-limit.middleware.ts`, `express-rate-limit`, in-memory): `/auth/login` 20/15min/IP, public registration 5/hour/IP, document scanner 20/hour/company, project attachment uploads 60/hour/company, template previews 300/15min/user, browser error reports 10/hour/user and 100/hour overall. Login compares against a dummy bcrypt hash for an unknown email (same response time as a wrong password - no email enumeration) and refuses an `is_active = false` account. Passwords: 8 characters minimum, 72 bytes maximum (bcrypt ignores anything past that), checked server-side.
- **Refresh tokens**: login returns an access token (`token`, 5h, `JWT_SECRET`) in the JSON body, and sets a refresh token (`refreshToken`, 7d, `JWT_REFRESH_SECRET`, hash-only stored in `refresh_tokens` so it can be revoked) as an `httpOnly` cookie (`docky_refresh_token`, `SameSite=Lax`, `Path=/`) via `cookie-parser` - never in the response body, frontend JS never touches it. `POST /auth/refresh` and `POST /auth/logout` read it from `req.cookies`, not the body. Not rotated — see [zz_docs/Decisions.md](../Decisions.md) for why. `JWT_REFRESH_SECRET` must be set in `backend/.env`. The cookie's `secure` flag comes from `COOKIE_SECURE` (`backend/.env`): `true` in prod (HTTPS + HSTS), unset locally (a Secure cookie is dropped over `http://localhost`). `POST /auth/refresh` reads the user again from the database (`getActiveUserByIdFromDB`) - a deleted or deactivated account gets nothing, and the new access token carries the account's current role/company/language, not the 7-day-old claims of the refresh token. Deleting a user revokes all its refresh tokens first (`005_cascade_user_deletion.sql` makes the delete itself possible: `refresh_tokens` cascade, `login_history` set null).
- **Employee permissions** (since 2026-11-18, `023_add_employee_permissions.sql`'s `employee_permissions`, one JSONB row per company, `modules/permissions`): the company's ADMIN sets, on **Paramètres > Droits des employés** (`/settings/permissions`, `GET`/`PUT /permissions/employees` - ADMIN/PLATFORM_ADMIN only), what every USER of the company may do per module - `clients`, `catalog`, `quotes`, `invoices`, `projects`, `calendar`, `dashboard` - `NONE` (hidden) / `READ` / `WRITE`, plus **`prices`** ("Voir les prix", since 2026-11-19): off, `normalizePermissions` forces `quotes`/`invoices`/`dashboard` to NONE (`PRICED_MODULES` - made of amounts, PDFs included; greyed out on the settings page), `app.ts`'s `hidePricesFromEmployees` nulls every price field in every JSON response to such a USER (`withoutPrices`: `unit_price`, `selling_price`, `purchase_price`, `discount`, `amount_excl_vat`/`_incl_vat`, the early payment discount, `amount_due`, `total_paid`, `estimated_amount` - tested; sent once their permissions are read, a failure there never escaping the request), and nothing they save sets a price: a chantier's content keeps each line's stored price by the `id` the frontend sends back (an id no longer there - the content saved meanwhile - is a 409, never a line repriced), a new catalog line the resource's selling price, a typed one 0 for the admin to price (`hidden-prices.ts`'s `keptLinePrice`, tested - `replaceDocumentContentServ`/`addLineServ`'s `keepPrices`), a resource edited keeps its prices and one created is unpriced. The screens hide the price columns (`PermissionService.canSeePrices`: resources, a chantier's resources and ledger, the calendar's section lines). The "Profil ouvrier" preset turns it off. ADMIN/PLATFORM_ADMIN are never bound (`FULL_PERMISSIONS`). No row: `DEFAULT_EMPLOYEE_PERMISSIONS` - everything but the dashboard and the calendar, what an employee could already do (both were ADMIN-only routes before). `permissions.ts` (pure, tested: `allows`, `normalizePermissions` - unknown modules/levels ignored, own properties only, a missing module its default - `moduleOfDocumentType`). Enforced on every business route by `permission.middleware.ts` (after `authenticate`, permissions read once per request into `req.permissions`): `requirePermission(module, level)` - GET READ, the rest WRITE; `requireAnyPermission` where another module needs the data (a client's name or address for quotes/invoices/chantiers/the calendar, the catalog for their pickers, project types); `requireDocumentPermission(level, locator, alsoAllowedBy?)` for anything touching one document - by its id, a section's or line's id, `document_id` in the query or body - checking its type's module (a PROJECT document is the chantier's), a chantier's section dates/note also allowed by `calendar` WRITE (a quote's or an invoice's never); `requireDocumentTypePermission` for `POST /document`; lists without a type (`GET /document`, `/document-complete`) only return readable types (`readableDocumentTypes`). Accepting a quote also needs `projects` WRITE (the frontend only offers "Acceptée" then); a chantier's billing/deposits `invoices`; the dashboard's cards their own module too; PDFs, the QR-bill slip and the scanner `quotes`/`invoices` - a document's PDF also its own type's module (`requireDocumentPermission`), and each generator refuses a document of another type (a 404: no quote printed through `/pdf/invoice/:id`). A refusal is a 403. Frontend: `shared/services/permission.service.ts`'s `PermissionService` (`GET /permissions/me` for a USER, reloaded when the user, company or role changes - not on a token refresh - and started by `ready()` itself too: a login navigates before an effect would run; everything for anyone else; nothing while loading) - `can(module, level)`, `features/auth/permission.guard.ts`'s `permissionGuard` on every business route (route data `permission`, `'documents'` reading `?type=`, `permissionLevel`; an employee not allowed lands on the first page they can read, `/` included), nav-bar links filtered per link, and read only on screen: no add/pencil/archive/duplicate/status change in the lists, the document form locked, a chantier's "Modifier"/"Clôturer"/files, the calendar not editable (no drag and drop, notes, planning tour or sections sidebar), cross-module requests skipped instead of failing (a chantier's invoices, the form's chantiers, the dashboard's cards, a section's lines). Tested: `employee-permissions.test.ts`. The weekly demo reset deletes company 2's row.
- **Cross-company access ("impersonation") — built**: `POST /auth/impersonate/:companyId` (`PLATFORM_ADMIN` only) issues a new access token with that company's own `company_id` swapped in, `role` staying `PLATFORM_ADMIN` — every endpoint's own `req.user.company_id` scoping does the rest for free. The frontend keeps the platform admin's real token in a second `localStorage` slot (`AuthService.impersonateCompany`/`returnToPlatformView`) to switch back without re-authenticating. Deliberately doesn't touch the refresh token at all — an impersonated session is capped at one access token's lifetime (5h); once it expires the frontend asks to pick the company again rather than risk `POST /auth/refresh` silently dropping back to the platform admin's own company.
- **User management is centralized to `PLATFORM_ADMIN`, not `ADMIN`** — `GET /user`, `DELETE /user/:id`, and `POST /user`'s authenticated "add an employee" branch (`user.service.ts`'s `createUserService`) all require `PLATFORM_ADMIN` now. An ordinary company `ADMIN` no longer manages their own company's users directly — a `PLATFORM_ADMIN` does it by impersonating that company first (deliberate choice, made once impersonation existed as an alternative). **Matters for the demo account** (see README's Live demo): it logs in as a plain `ADMIN`, on purpose, never `PLATFORM_ADMIN` — a recruiter using it never sees `/settings/users`, `/settings/users/new`, `/settings/login-history`, `/settings/companies`, `/settings/errors` or `/settings/uitest`.
- **No self-service way to create a `PLATFORM_ADMIN`** — inserted by hand in the DB. `POST /user`'s public registration path always forces `role = 'ADMIN'`.
- `company.routes.ts` has its own ownership checks (comparing `req.user.company_id` to `req.params.id`, so not in the generic role middleware): reading is open to any role of that company, editing needs that company's own `ADMIN` — both also let `PLATFORM_ADMIN` through regardless of company.
- `POST /user` has no `authenticate` deliberately — it's both public "register a new company" (unauthenticated: takes a `companyName` and creates the company *and* its first `ADMIN` in one transaction - it never takes a `company_id`, so nobody can claim an existing company) and "an authenticated `PLATFORM_ADMIN` adding an employee" (forces `company_id` from the token, role `ADMIN` or `USER` only - never `PLATFORM_ADMIN`). `POST /company` is `PLATFORM_ADMIN` only now; the frontend's registration is the single `POST /user` call. Don't split into two routes — registration has to be reachable with no token.
- **`login_history`**: every login attempt (successful or not) is recorded (`auth.service.ts`'s `authUserService`, best-effort - a write failure never blocks login itself), readable via `GET /login-history` (`PLATFORM_ADMIN` only, not scoped to one company), filtered server-side by `?user_id=` (the page's user picker, fed by `GET /login-history/users` - every user with at least one attempt). Attempts against an unknown email, and those of a since-deleted user (`user_id` set null), only show unfiltered.

## Frontend

- **Auth token refresh**: only the access token lives in `localStorage` (`docky_token`) - the refresh token is an httpOnly cookie the browser handles on its own (see Backend), `AuthService` never reads/stores it. `login`/`refresh`/`logout` all pass `withCredentials: true` so the cookie is sent/received. `auth.interceptor.ts` catches a 401 (except on `/auth/login`/`/auth/refresh`), refreshes, retries once; dedupes concurrent 401s into one `/auth/refresh` call. `logout()` also revokes server-side (best-effort).
