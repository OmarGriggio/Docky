# App shell, dashboard and phone layout

Navigation (rail and phone bottom bar), account menu, the dashboard, the invoicing readiness banner, the calendar's phone behaviour, guided tours, PWA and the help button.

Moved out of CLAUDE.md on 2026-11-26 - keep it up to date in the same commit as the code it describes.

## Backend

- **Dashboard** (`modules/dashboard`): `GET /dashboard/open-invoices` (every SENT invoice, archived included - the client still owes it - earliest due date first; the frontend sums them on the table's last line) and `GET /dashboard/projects-in-progress` (active IN_PROGRESS chantiers, in the chantiers list's own "closest section date" order, with their ledger's amount excl. VAT), next to `paid-by-client`. Each row carries the client's name columns plus the document's `recipient_name`, resolved to one name by the frontend.

## Frontend

- **"Complète ton profil pour pouvoir facturer"**: `shared/components/invoicing-readiness-banner` on the dashboard and the profile, while the company lacks what invoicing needs (`invoicing-readiness.ts`'s `missingForInvoicing`, tested): what its QR-bill needs - name, IBAN, NPA + town, country, the street being optional there - so it's found out before a PDF fails with a 422, and its VAT number when it charges VAT (`vat_rate` > 0 - an invoice charging VAT must print it). Only an ADMIN/PLATFORM_ADMIN gets the link to the profile.
- **Account navigation**: `nav-bar`'s bottom item (the user's email) opens a flyout popup - **Paramètres** (→ `/settings`), **Profil** (→ `/profile`), a thin separator, **Déconnexion**. `/profile` is a single page, just the "Mon entreprise" form (`CompanyProfile`). `/settings` (`Settings`, a `p-menu` side layout) lists Modèles (→ `/settings/templates`, the templates - see [templates.md](templates.md)), Numérotation (→ `/settings/numbering`, see [numbering.md](numbering.md) - every role reads it, only an admin saves), Droits des employés (→ `/settings/permissions`, ADMIN/PLATFORM_ADMIN only, a "Profil ouvrier" preset), Langue (→ `/settings/language`) and, for `PLATFORM_ADMIN` only, UI Kit/Entreprises/Utilisateurs/Nouvel utilisateur/Historique des connexions/Erreurs. It used to be all under `/profile`.
- **nav-bar is a collapsible icon rail**, not text links: one `pi` icon per page, PrimeIcons, `height: 100vh`, `position: sticky`. A toggle button at the top (`NavBar.expanded`, persisted per-browser in `localStorage` as `docky_nav_expanded`) switches between collapsed (64px, label shown as a hover tooltip) and expanded (224px, label always visible inline - long labels ellipsize via `truncate`, not wrapped). Click on a multi-link item (Documents, Ressources) opens a `<details>` flyout with the sub-links, closed either by clicking a link or anywhere else on the page (`NavBar`'s own `document:click` listener). Fully Tailwind utility classes now (`nav-bar.css` is empty, see CLAUDE.md's CSS bullet) - no PrimeNG `p-tooltip`/`p-menu` here though, same reasoning as before: trying those first added ~99kB to the *initial* bundle (nav-bar is eagerly loaded as part of the app shell, and neither was used anywhere else yet, so their whole overlay/positioning machinery landed in the eager bundle). **Gotchas**: `nav` needs its own explicit `z-index` (not just `position: sticky`, which alone leaves it `z-index: auto`) - without one, `nav`'s whole subtree competes against page content purely by DOM order at the outer stacking level, and no amount of z-index on a *descendant* tooltip fixes that. This project has no bridge between PrimeNG's own `--p-surface-*` theme variables and Tailwind (no `tailwindcss-primeui` plugin, no `@theme` block) - a `surface-*` Tailwind class (`text-surface-500` etc.) silently compiles to nothing; use Tailwind's own palette (`gray-*` etc.) instead. And a flex item's default "never shrink below content size" floor is real: an expanded rail item needed both `min-w-0` *and* an explicit `md:w-full` (not just the parent's `items-stretch`, which measured 3px short in practice) to keep a long label from pushing its own hover background/border past nav's own right edge - apply both, at the exact same element, together.
- **On a phone (below Tailwind's `md`, 768px) nav-bar is a fixed bottom bar** instead of the rail: icons only (no toggle, no logo, no labels), flyouts and the account popup open upward, `env(safe-area-inset-bottom)` padding for the iPhone home indicator; `app.css` stacks `.layout` vertically, clips anything wider than the screen (`overflow-x: clip` - one overflowing element widens a phone's layout viewport and pushes the fixed bar off-screen) and pads `.content`'s bottom so nothing hides behind the bar. The breadcrumb (`app-header`) is hidden on phones. FullCalendar's own CSS is unlayered, so it beats Tailwind's utilities - a Tailwind class overriding it needs `!`. Its toolbar buttons are white with a green outline (`calendar.css`'s `--fc-button-*`), only "+ Note" solid green; the "Sections à planifier" cards look like the blue section events they become. "Comment planifier ?" (desktop only, an icon with its label on hover) starts a guided tour over the page itself, by itself on a browser's first visit (`docky_calendar_guide_seen` in `localStorage`): `shared/components/guided-tour` (no library) dims the page but the step's element - a CSS selector, the page's `data-tour` marks or FullCalendar's own toolbar, a step without one in the middle - with a card beside it (Previous/Next, Escape, arrows); a step's target can be a list tried in order (an element not there yet, then one that always is). The quote/invoice form has one too ("Comment remplir ?", 12 steps from the recipient to the status bar, worded per type - `document-form.ts`'s `guideSteps`, `docky_document_guide_seen`, by itself the first time a new document is opened). A document started from scratch opens with one empty section (`document-draft.ts`'s `blankSection`, part of its clean state - leaving it untouched isn't unsaved work), dropped if still untouched when a chantier's resources are loaded in (`isBlankSection`, tested). A text shown in a tour never quotes a `{{placeholder}}` literally (Transloco would drop it, see CLAUDE.md's i18n bullet). The calendar follows the same breakpoint (`BreakpointService.isMobile`, see CLAUDE.md's Phone layout bullet): week list view (`@fullcalendar/list`) with a Liste/Mois switch in the footer, no drag-and-drop, no "Sections à planifier" sidebar, and "+ Note" (next full hour, one hour long) - a p-button above the calendar on desktop, a FullCalendar custom button in its own toolbar on a phone (`customButtonsFor`, buttons shrunk with `max-md:[&_.fc-button]:...!`). On a phone the note form edits start/end as four native `type="date"`/`type="time"` inputs (the iPhone's own wheels - `note-time.ts`, moving the start drags the end along), and a day tapped in the month view starts at 8:00 for an hour. **Gotcha**: a `p-datepicker` inside a `p-dialog` needs `[autofocus]="false"` - PrimeNG's `pAutoFocus` only removes the attribute for an explicit `false`, an unset input renders `autofocus="true"` and the browser opens that picker as soon as the dialog shows.
- **PWA - installable on a phone's home screen**: `@angular/service-worker` (`provideServiceWorker` in `app.config.ts`, prod builds only - never under `ng serve`), `ngsw-config.json` caches the app shell (JS/CSS/`i18n/*.json`/images) and never touches `/api/**` (no `dataGroups`: data always comes from the network, the app just opens offline). `public/manifest.webmanifest` + `public/icons/` (192/512 + `apple-touch-icon.png` 180, all generated from `zz_brand/docky-icone-vert-sur-blanc.png` on an opaque white background), theme color `#037a3f` (the logo's own green). `frontend/nginx.conf` serves `ngsw-worker.js`, `ngsw.json` and the manifest with `no-cache` (they keep the same name between builds - the one-year immutable rule would freeze an installed app on an old version) and gives the manifest its MIME type, missing from nginx's own `mime.types`. A frontend `nginx.conf` change ships with the frontend image, no gateway restart needed.
- **`app-help-button`** (`shared/components/help-button/`): a reusable "?" icon button - click opens a `p-popover` showing whatever's projected into it via `ng-content`. Unlike nav-bar, safe to use PrimeNG's own overlay (`Popover`) here since this only ever lives inside already-lazy feature pages - its weight lands in that page's own chunk, not the initial bundle.
