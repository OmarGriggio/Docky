# Clients

Creating and importing clients, the clients list and form, and the NPA/town suggestions every address field uses.

Moved out of CLAUDE.md on 2026-11-26 - keep it up to date in the same commit as the code it describes.

## Backend

- **Creating a client** (`POST /client`): email optional (an empty one stored as `NULL`, the uniqueness check skipped). An optional `address` (attention optional, street + postcode + town + country required - a 400 otherwise) becomes the client's primary address, created in the same transaction as the client.
- **Importing clients from a spreadsheet** (`POST /client/import`, since 2026-11-13; the frontend side is the Frontend's "Client import" bullet below): `{ rows, defaultCountry, language }`, at most 1000 rows (a 400 `TOO_MANY_ROWS`), a 2 MB body read by the route itself once authenticated and rate-limited (`client.routes.ts`; `app.ts`'s generic 100 kB parser skips that path; nginx allows 10 MB), 120 calls an hour per company and 10 real imports on top (`clientImportWriteRateLimiter`), one real import at a time per company (`pg_try_advisory_xact_lock`, a 409 otherwise - never left waiting with a connection held), written in two statements (`createClientsInDB`/`createPrimaryAddressesInDB`, `unnest`), not one INSERT per row. Every rule is in `client-import.ts`'s `checkImportRows` (pure, tested) and returns per row the client and address it becomes plus **errors** (blocking: a required name missing, a value too long for its column - never cut, an invalid email, an email or number the company already has or the file repeats, an incomplete address) and **warnings** (imported as shown: a full name put in the last name, a type/language/title not recognized or interpreted, a former number moved to the note, a probable duplicate - same name and NPA, a last name ending in a legal form, a company given for an individual, a phone's lost leading 0 put back, an unusual NPA, a country `toIsoCountryCode` can't map), each an `{ field, code, params }` the frontend translates. A cell that isn't a string/number/boolean or carries control characters is an error, never a 500; types and languages are looked up in `Map`s (a cell reading `constructor` finds nothing); "-", "/" read as empty; the email pattern is linear and only tried once the email fits its 255 characters (it was a ReDoS). A building number in its own column (`house_number`) follows the street. No language in the file means the user's own (and the title written in it). **Client numbers**: digits or a number already in the company's format, whatever its case or padding (6 digits at most - a bigger number would push every generated one that far) become that sequence in the format (`867` → `C0867`, `c1` → `C0001` with the default `C{NNNN}`), anything else from the file goes into the note ("Ancien n° : ...") and a number is generated, while typed by hand in the preview (`client_number_edited`) it's an error; no type means professional when there's a company, individual otherwise. `?dryRun=true` (the preview) writes nothing; a real import checks again under the client numbering lock, then creates every row or none (a 422 with the same report if any row has an error): rows keep their number, the others get the next ones after the highest there is then.

## Frontend

- **Clients list and form**: two tabs, Professionnels / Particuliers (`client-list.ts`'s `activeType`, filtering the same table - professionals show the company, individuals first + last name, both followed by the client's primary address - or its oldest one - as Rue/NPA/Ville columns from `getClientsFromDB`'s `LEFT JOIN LATERAL`, edited with the rest of the row (the pencil: street + NPA + town or nothing, a client without an address gets a primary Swiss one); no Type column, the tab says it - a client has no VAT number since `012_drop_client_vat_number.sql`, only the company's own is printed); "+" opens the form on the active tab's type. No client number field - it's generated (see Backend). Required: the company for a professional or the last name for an individual, and street + NPA + town once an address is added (see CLAUDE.md's required fields bullet). The form's "Civilité" is a select (Masculin/Féminin/Non défini) storing `Monsieur`/`Madame` in a French UI, `Mr`/`Ms` in an English one (like each company's seeded clients) and nothing for "Non défini" - it's printed as is on the PDFs (above an individual's name, and as the greeting, which falls back to the client language's "Madame, Monsieur"). "Ajouter une adresse" shows the address fields (sent with the client, see Backend); the country isn't asked, always `clients.form.defaultCountry` (Suisse/Switzerland - only Swiss addresses for now).
- **NPA suggestions**: every address typed in the app has **one "NPA et ville" field** - the client form, the shared `address-form`, a document's typed-in recipient, the company profile, the QR-bill slip's payer, and the clients list's and a client's addresses' row editors (a per-row draft, split back on save) (`shared/components/postal-code-city`, a `ControlValueAccessor` around `p-autocomplete`, its value plain text): typing an NPA or a town suggests "NPA Town", picking one fills it, anything can still be typed; `postal-code-search.ts`'s `splitPostalCodeCity` turns "1950 Sion" back into the NPA and the town an address stores (`POSTAL_CODE_CITY_PATTERN` - both required). Street fields read "Rue et n° du bâtiment". Its width follows its neighbours: natural in a two-column `.ui-form`, `[fluid]="true"` where they fill their cell or column. The data is a static file, `public/data/swiss-postal-codes.json` (~90kB, `[npa, town]` pairs, fetched once by `PostalCodeService` when a form needs it, cached by the service worker), generated from swisstopo's official directory of localities (open data, credit "© swisstopo") by `node scripts/generate-swiss-postal-codes.mjs` - rerun it now and then, commit the result. One NPA can have several towns (and one town several NPAs), hence a pick rather than a lookup. Search: `shared/utils/postal-code-search.ts` (tested).
- **Client import** (`/clients/import`, from the clients list's ⋮ menu - `list-toolbar`'s `extraMenuItems`): the file (`.xlsx` via `read-excel-file`, `.csv` via `papaparse` guessing the separator, a CSV decoded as UTF-8 or else Windows-1252 - both libraries imported dynamically, so they only load once a file is picked) is read in the browser, never uploaded (`client-import/spreadsheet-reader.ts`), a sheet picked when there are several. A file over 10 MB is refused before it's read. Its header row is the first with two cells filled (a title line above the table is skipped), each column matched to a Docky field from its header (`import-columns.ts`'s `guessMapping`, French/English/German synonyms, accents and punctuation ignored, a bare "N°" being the building number - never the client number, tested), every match changeable or ignored, one column per field. Then the preview (`client-import-preview`): every row kept (a checkbox) checked by a dry run (`?dryRun=true`), each cell editable - outlined red for an error on its field, orange for a warning, the backend's messages translated from their codes (`clients.import.issues.*`) in the row's last column, the number the client will get under its number cell (that column always shown, a number typed there being `client_number_edited`). The verdicts start stale (nothing importable unchecked) and any change marks them stale again until "Vérifier à nouveau" - a check answering after a change made meanwhile leaves them stale (a version counter); "Exclure les lignes en erreur" leaves those out and checks again; filters All/Errors/Warnings/Left out, 50 rows a page. "Importer" only once the kept rows were checked with no error; a 422 (a row turned wrong meanwhile) shows its verdicts, nothing created. Leaving the page once a file was read asks first (`unsavedChangesGuard`, plus `beforeunload`), going back to the columns too when the preview was edited (its edits are rebuilt from the file), a success toast and back to the clients list once imported.
