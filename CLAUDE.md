# Docky — Working conventions

Solo learning project (SaaS for small construction companies). See [README.md](README.md) for the full pitch, stack and domain model — this file is about *how to work in this repo*, for Claude and future contributors.

## Workflow

- **Git**: day-to-day work happens on `develop` (started 2026-10-09) — `main` is the deploy branch CI watches (see Deployment), kept for stable/ready work, merged into from `develop` once a feature or a batch of commits is ready to ship. Not a per-feature-branch model - one shared `develop`, no feature branches off it either. Only commit or push when explicitly asked, and never push without an explicit go-ahead even after committing - this applies to merges into `main` too, since that's what triggers an auto-redeploy.
- **Before every merge of `develop` into `main`**: run the three review subagents in [.claude/agents/](.claude/agents/) - `business-reviewer`, `security-reviewer`, `code-reviewer` - in parallel on what isn't on `main` yet (`git log origin/main..develop`, `git diff origin/main..develop`), report their findings, fix whatever is blocking, and only then merge (still with an explicit go-ahead). Systematic since 2026-10-26: the first such pass caught two blocking bugs (a connection-pool deadlock, an empty invoice locking a chantier) that tests and manual checks had missed.
- **Commit messages**: `<Area> : <what changed>` (e.g. `Backend : scope client lookup by id and delete to the caller's company`), capitalized, English, imperative/present tense, no trailing period. Areas so far: `Backend`, `Frontend`, `Docs`.
- One commit per module per side — a backend change and its matching frontend change are two separate commits.
- **English everywhere** — code identifiers, DB tables/columns, doc filenames and content (migrated from French, complete as of 2026-09-02; see [zz_docs/Decisions.md](zz_docs/Decisions.md) for the glossary). **Exceptions, content not naming**: the frontend's user-facing text is French by default (company 1's own convention) but translatable (see Frontend's Transloco bullet) - don't "fix" a French UI string into English, add an `en.json` key instead. The seed data in `zz_migrations/001_data.sql` follows whichever company it belongs to: company 1's stays French (the developer's own company), company 2's (the demo company) is deliberately English - see that file's own header comment and the Backend's "Seed data" bullet for why.

## Backend (`backend/`)

- Express 5 + TypeScript, run via `tsx watch src/server.ts` (`npm run dev`). No ORM by design — raw SQL through `pg` via a repository layer (see [zz_docs/Architecture.md](zz_docs/Architecture.md) before introducing one).
- **Feature-module structure**, not the flat `controllers/`/`services/` layout the README sketches:
  ```
  backend/src/modules/<domain>/<name>.controller.ts
                                <name>.service.ts
                                <name>.repository.ts
                                <name>.routes.ts
                                <name>.types.ts
  ```
  `controller → service → repository`. Current modules: `auth` (+ `login_history.*`, `refresh_token.*`), `users`, `companies`, `clients` (+ `address.*`), `catalog` (`resource.*`, `resource_unit.*`), `projects` (+ `project_type.*`, `project_attachment.*`), `documents` (`document.*`, `document_complete.*`, `document_line.*`, `document_section.*`, `document_template.*`), `calendar` (`calendar_note.*`), `dashboard`, `document-scanner`, `health`, `error-log`. Suppliers and supplier prices were dropped.
- **Transactions**: `shared/config/database.ts`'s `withTransaction(work)` runs `work` in one transaction; repositories query through `db()` (not `pool` directly), which resolves to the running transaction's own connection via `AsyncLocalStorage` - so a multi-step service just wraps its body, no `client` parameter threaded through. A nested call joins the outer one. Used by `acceptQuoteServ`, `addProjectServ`, `addDocumentServ` (its numbering lock, see the document numbers bullet), `replaceDocumentContentServ`. **Every repository must query through `db()`, never `pool` directly**: a `pool` query inside a transaction holds the transaction's connection while waiting for a second one - ten concurrent saves were enough to deadlock the whole pool before this was fixed. The pool also has a 5s `connectionTimeoutMillis`, so running dry is an error rather than a frozen server. `replaceDocumentContentServ` locks its document (`getDocumentByIdForUpdateFromDB`, `SELECT ... FOR UPDATE`) so a concurrent save or status change waits for it.
- **`resources.type` is `MATERIAL | SERVICE`** only (simplified from `MATERIAL | LABOR | SUBCONTRACTING | OTHER`), matching `document_lines.type`.
- **Chantiers list ordered by urgency**: `project.repository.ts`'s `getProjectsFromDB` sorts `IN_PROGRESS` projects by the `date_start` (among that chantier's own sections) closest to right now - either direction, an overdue section is just as worth surfacing as an upcoming one - via a `LEFT JOIN LATERAL` picking the single closest one per project (a plain `MIN()` can't express "closest to now", only "earliest overall"); `COMPLETED` projects always sort last regardless of their own dates. Exposed as `closest_section_date` on the list response.
- **A chantier is a `PROJECT` document**: every `projects` row owns exactly one `documents` row of type `PROJECT` (`projects.document_id`), whose sections/lines are the chantier's resource ledger (`project_resources` is gone). Accepting a quote (`acceptQuoteServ`) creates both and copies the quote's resource-backed lines into it; a hand-created chantier starts empty. `document-form.ts`'s "Charger chantier" prefills an invoice from that ledger.
- **Document lifecycle, enforced server-side** (the frontend locks the same cases, but this is the real rule):
  - Statuses: a quote `DRAFT`/`SENT` → `ACCEPTED` (only via `POST /document/:id/accept`, creates the chantier) or `REJECTED`; an invoice `DRAFT` → `SENT` → `PAID` or `CANCELLED`, forward only (a `SENT` invoice never goes back to `DRAFT`). Allowed transitions per current status: `SETTABLE_STATUSES`. `POST /document` always creates an active `DRAFT`, whatever the body says. `discount`/`vat_rate` must be 0-100.
  - Header and content (sections/lines) are editable only while a quote is `DRAFT`/`SENT`, an invoice is `DRAFT` (`isOpenForEditing` - once sent, the client holds it under its number: a wrong one is cancelled and duplicated, not rewritten), or a `PROJECT`'s chantier is `IN_PROGRESS` - `assertContentEditableServ`, checked by every line/section write. A section's dates and calendar note stay editable (planning, not content).
  - A `COMPLETED` chantier is invoiced once: a second `POST /document` with the same `parent_document_id` is a 409, unless the earlier invoice was cancelled (an archived one still counts - archiving tidies a list, it doesn't undo an invoice). The project list shows "Voir la facture" instead of "Facturer" then.
  - A status change (`updateDocumentStatusInDB`) also requires `DRAFT`/`SENT` and an active document in the `UPDATE` itself, so it can't overwrite a concurrent accept.
  - Accepting a quote flips its status first, inside the transaction, with the `DRAFT`/`SENT` check in the `UPDATE` itself (`acceptDocumentInDB`) - a concurrent second accept matches nothing, so one quote never spawns two chantiers.
- **A document without a client from the list ("Saisie manuelle")**: every company has exactly one **"Non défini"** client (`clients.is_placeholder`, `007_add_placeholder_client.sql`, created with the company by `company.service.ts`'s `addCompanyServ`) - protected (no edit, archive or address: 409), hidden from the clients list and every client picker. A quote/invoice made out to it carries its recipient typed by hand on the document itself (`recipient_name`/`_complement`/`_street`/`_postal_code`/`_city`, `008_add_document_recipient_columns.sql`; name + postcode + town required, no control characters, complement + street together within the QR-bill's 70-character address line - `document.service.ts`'s `resolveRecipient`; always null for a real client). PDFs, the QR-bill and the reminder print that recipient instead of the client (`pdf/templates/dto/shared.ts`'s `buildClientDto`); greeting "Madame, Monsieur", language FR and country Switzerland come from the placeholder. Accepting such a quote carries the recipient onto its chantier, named after it. Company 2's (the English demo's) placeholder is "Not specified" / "Dear Sir or Madam" / EN instead - set by 007 and kept that way by the weekly demo reset; the UI shows the translated `clients.placeholderName` wherever a client name would be (dashboard, chantiers), and a chantier's detail and Lieu column show its typed-in recipient. `documents.client_id` stays `NOT NULL` - see [zz_docs/Decisions.md](zz_docs/Decisions.md) for why this over a nullable client or one auto-created client per document.
- **Saving a document's content**: `PUT /document/:id/content` takes the whole draft (`{ sections: [{ title, description, date_start, date_end, note, lines: [...] }] }`), archives every current section/line and recreates them in one transaction, then recomputes totals once. Both `document-form.ts` and `project-resources.ts` save through it (`DocumentService.replaceContent`) - never one request per line again. Line types, labels, quantities, prices, a line's own discount (0-100), section titles, a 500-line cap and a line's `resource_id` (must be the company's own) are validated there; `document_lines.type` has no CHECK constraint of its own.
- Auth: JWT (`jsonwebtoken` + `bcrypt`), guard in `shared/middlewares/auth.middleware.ts`. Rate limits (`shared/middlewares/rate-limit.middleware.ts`, `express-rate-limit`, in-memory): `/auth/login` 20/15min/IP, public registration 5/hour/IP, document scanner 20/hour/company, project attachment uploads 60/hour/company, browser error reports 10/hour/user and 100/hour overall. Login compares against a dummy bcrypt hash for an unknown email (same response time as a wrong password - no email enumeration) and refuses an `is_active = false` account. Passwords: 8 characters minimum, 72 bytes maximum (bcrypt ignores anything past that), checked server-side.
- **Refresh tokens**: login returns an access token (`token`, 5h, `JWT_SECRET`) in the JSON body, and sets a refresh token (`refreshToken`, 7d, `JWT_REFRESH_SECRET`, hash-only stored in `refresh_tokens` so it can be revoked) as an `httpOnly` cookie (`docky_refresh_token`, `SameSite=Lax`, `Path=/`) via `cookie-parser` - never in the response body, frontend JS never touches it. `POST /auth/refresh` and `POST /auth/logout` read it from `req.cookies`, not the body. Not rotated — see [zz_docs/Decisions.md](zz_docs/Decisions.md) for why. `JWT_REFRESH_SECRET` must be set in `backend/.env`. The cookie's `secure` flag comes from `COOKIE_SECURE` (`backend/.env`): `true` in prod (HTTPS + HSTS), unset locally (a Secure cookie is dropped over `http://localhost`). `POST /auth/refresh` reads the user again from the database (`getActiveUserByIdFromDB`) - a deleted or deactivated account gets nothing, and the new access token carries the account's current role/company/language, not the 7-day-old claims of the refresh token. Deleting a user revokes all its refresh tokens first (`005_cascade_user_deletion.sql` makes the delete itself possible: `refresh_tokens` cascade, `login_history` set null).
- **File storage is MinIO/S3** (`shared/storage/storage.service.ts`, a `minio` service in both compose files, `S3_*` in `backend/.env`): company logo/header image (`companies/{id}/logo.jpg`...) and project attachments (`companies/{id}/projects/...`), uploaded through `multer` in memory. `GET /uploads/*splat` (`app.ts`) is public on purpose (`<img>` tags send no token) but only serves keys matching the logo/header pattern - attachments go through their own authenticated, company-scoped route. `shared/storage/purge-company-files.ts` deletes one company's whole prefix (used by the weekly demo reset). **A storage key never comes from a request**: attachments rebuild theirs from the DB row (`buildAttachmentKey`), and `companies.logo`/`header_image` are only ever set by their own upload routes - `PUT`/`POST /company` ignore them (a key typed by hand could point at another company's private attachment and get it embedded in a PDF), and the PDF generators only read `companies/{that company}/logo|header.jpg|png` anyway (`readCompanyImage`).
- **PDFs** (`backend/src/pdf/`): invoice (with Swiss QR-bill), quote, payment reminder (with QR-bill). Template Method in `generators/document-pdf-generator.ts`; invoices and quotes laid out by `templates/business-letter.ts` (see the layout bullet below), the reminder by its own letterhead in `templates/letter.ts`, DTO building in `templates/dto/shared.ts`. Printed in the **client's** language (`clients.language`, not the user's UI one): every fixed string is in `templates/pdf-labels.ts` (`PDF_LABELS.FR`/`.EN`), DE/IT fall back to French. Totals printed are the stored `amount_excl_vat`/`amount_incl_vat` - never re-added in a template - and per-line/section totals use `document.calculations.ts`'s `lineTotal` (line discount included), so the PDF always matches the app. The QR-bill's `country` is mapped from free text to ISO (`swiss-qr-bill.dto.ts`'s table: Suisse/Switzerland/Schweiz/Svizzera...) - a country name missing from it makes the QR-bill fail.
- **QR-bill errors are a coded 422**, not a 500: `SwissQrBillValidationError` (an `AppError`) carries `COMPANY_IBAN_MISSING`/`COMPANY_IBAN_INVALID`/`COMPANY_ADDRESS_INCOMPLETE`/`QR_BILL_AMOUNT_INVALID`/`QR_BILL_INVALID` as `code` in the JSON body (`AppError`'s optional third argument, see `shared/types/errors.ts`), which the frontend maps to a translated `qrBillErrors.*` message (`shared/utils/api-error.ts` - a PDF error body arrives as a Blob). The company IBAN is stripped of spaces first.
- **Invoice and quote layout** (`pdf/templates/business-letter.ts`, shared by both - a change there applies to both): modelled on the company's own Excel invoices. Page 1: client number and place/date (`03.09.2024`) left, title + address right, intro, "FACTURE/OFFRE N° ..." underlined, "Réf." (`reference_client`), one line per section ("Pos 1"...) with its total, then the totals as a borderless table (Total / Rabais % / TVA N° % / **Total** between two rules / an invoice's early payment line), the conclusion, and a block anchored just above the footer (an invoice's payment conditions; a quote's validity + the company's payment terms, after its "Bon pour accord" lines). Page 2+: numbered sections ("Pos 1 – ..."), then the same totals. Amounts as `1'578.75` (`templates/format.ts`). The header image is on every page (`PdfWriter.setPageDecorator`), the footer (company name/address/bank+IBAN left, website/email/phone right) on every page but the QR-bill's (`forEachNumberedPage` - the pages left out of numbering), and flowing text stops above it (`setBottomLimit`). The reminder still uses the older `letter.ts` layout. Every string drawn or measured goes through `PdfWriter`'s `printable`: the standard Helvetica fonts only cover WinAnsi, anything else (an emoji typed in a field) becomes "?" instead of failing the whole PDF.
- **Early payment discount ("escompte")** (`010_add_early_payment_discount.sql`): rate %, days and a minimum total incl. VAT on the company (profile form), copied onto an invoice when it's created (`addDocumentServ`, never from the request body) and frozen there like `vat_rate` - not editable per invoice yet, and a draft created before the company set one has none. `document.calculations.ts`'s `computeEarlyPayment` (rate% of the total incl. VAT, to the cent - not rounded to 5 centimes, on purpose for now). Printed only; the QR-bill always asks for the full amount. The footer's website/bank name/bank account are `009_add_company_footer_details.sql`.
- **Dashboard** (`modules/dashboard`): `GET /dashboard/open-invoices` (every SENT invoice, archived included - the client still owes it - earliest due date first; the frontend sums them on the table's last line) and `GET /dashboard/projects-in-progress` (active IN_PROGRESS chantiers, in the chantiers list's own "closest section date" order, with their ledger's amount excl. VAT), next to `paid-by-client`. Each row carries the client's name columns plus the document's `recipient_name`, resolved to one name by the frontend.
- **Standalone QR-bill slip** (`/qr-bill` page, `POST /pdf/qr-bill-slip`, `pdf/qr-bill-slip.ts`): a bare payment slip for a payer typed in or picked from the clients, optional amount, no document behind it - rendered as an SVG at its official 210 × 105 mm (`pdf/templates/swiss-qr-bill.svg.ts`, the guidelines' own font sizes and blank-field sizes, scissors on the cutting lines). The page turns it into a 300 dpi PNG and copies it to the clipboard as both `image/png` and an HTML `<img>` sized in mm, so Word/Excel paste it at its real size. A line too wide for the receipt column (measured with pdf-lib's Helvetica metrics) is a 400. Combined (`K`) addresses, like the invoice's own QR-bill - the address complement is folded into address line 1 in the payload, printed on a line of its own.
- **Document numbers are server-generated**: `document.service.ts`'s `generateDocumentNumber` builds `{OFF|FAC}-{year}-{4-digit sequence}` (French prefixes — printed content, not a code identifier), scoped per `company_id`+`type`+year, backed by `UNIQUE (company_id, number)`. `POST /document` ignores any client-supplied `number`. Sequence found via `LIKE`+`ORDER BY`, not a counter table (see [zz_docs/Decisions.md](zz_docs/Decisions.md) for why), under a per company+prefix advisory lock (`lockDocumentNumberingInDB`, `pg_advisory_xact_lock`) held until the transaction inserting the document commits - so `generateDocumentNumber` is only ever called inside `withTransaction`, the insert in the same one. `addDocumentServ` takes it before its "already invoiced" check, so two invoices for one chantier created at once take turns too.
- **Documents have real sections**: `document_sections` is a grouping title every `document_lines` row belongs to via a required `section_id` (replaces an earlier flat-list-with-marker-line approach — reopened, see [zz_docs/Decisions.md](zz_docs/Decisions.md)). `document_lines.type` is `MATERIAL`/`SERVICE` only, both always priced (`quantity`/`unit_price` `NOT NULL`), both using `quantity`+`unit` for their amount (e.g. `"5 Heure"` for a service — no separate time field). `position` is scoped to the line's section; `document_sections.position` orders sections. `addLineServ` checks the given `section_id` belongs to the target document.
- **Rounding**: each line is rounded to the cent first (`document.calculations.ts`'s `lineTotal`, half up via `round2` with `Number.EPSILON`), and `amount_excl_vat` is the sum of those rounded lines with the document discount applied - the same rule as the form (`document-draft.ts`) and the PDF, so lines, section subtotals and the stored total always add up exactly.
- **VAT**: `documents.vat_rate` (one rate per document — Switzerland has a single standard rate) applied on `amount_excl_vat` by `computeDocumentTotals`. **Payment terms**: `payment_terms` (free text) + `due_date` (structured), set directly, no computation.
- **`document_templates`**: default introduction/conclusion per `(company_id, type)`, at most one row each. `GET /document-template?type=X` (`null` if unset), `PUT /document-template/:type` (upsert). For `QUOTE`/`INVOICE`, purely client-side convenience — `document-form.ts` fills a new document's fields from it on type pick. `REMINDER` is the exception: the reminder PDF reads it every time, falling back to `document_template.defaults.ts`'s default text in the client's language. Edited from `/settings/templates` (see Frontend).
- **Schema changes are incremental migration files, not edits to `000_base.sql`** — `000_base.sql` is the whole schema as of 2026-09-24: while nobody used the app yet (no live database to upgrade), the first migrations (002-012: company header image/VAT/payment terms, resource code unique when active, section note, resource units, calendar notes, template due days/REMINDER type) were folded into it and deleted, and the seed data rewritten to match. From then on it is a frozen snapshot again (plus `001_data.sql`'s seed data right after it) - once the app has real data, don't fold again. A schema change gets its own new file, numbered next (`002_...`, `003_...`, one change per file, named for what it does, `ALTER TABLE`/etc, idempotent - e.g. `ADD COLUMN IF NOT EXISTS` - so it's harmless to ever re-run by hand). Two mechanisms apply them, deliberately redundant: Postgres' own `docker-entrypoint-initdb.d` runs every file in [zz_migrations/](zz_migrations/) in order, but **only on a brand-new empty volume** (first-ever startup); `backend/src/shared/migrations/migrate.ts`'s `runMigrationsServ()` (called from `server.ts` before the server starts accepting requests) additionally applies any file not yet recorded in the `schema_migrations` table it maintains, skipping `000_base.sql`/`001_data.sql` (the bootstrap, never re-run here) - so on an already-initialized dev or prod database (the normal case), a new migration just needs a backend restart (`docker compose up --build -d` / a redeploy) to take effect automatically, no manual `psql -f` step. Requires `zz_migrations/` bind-mounted read-only into the backend container (see `docker-compose.yml`/`.prod.yml`) - add it there too if a future compose file needs it.
- **Seed data** ([zz_migrations/001_data.sql](zz_migrations/001_data.sql)) runs right after `000_base.sql` on every fresh volume — a full sample dataset so there's always something to look at. **Dev logins, all `password123`**: `admin@dedonnostyle.ch` (`ADMIN`), `user@dedonnostyle.ch` (`USER`), `platform-admin@docky.ch` (`PLATFORM_ADMIN`); the demo company (company 2, Rénov Alpes) has `admin@demo.docky.ch` / `Demo2026!`, defaults to the English UI (`users.language`) and its whole content (clients, resources, documents, chantiers...) is in English, not French like company 1 - a recruiter is far more likely to read English (see that file's own header comment). **`clients.language`** (same migration as `users.language`, FR/EN/DE/IT - a client's own preferred language for correspondence, not tied to Transloco's FR/EN-only UI scope) defaults to `'FR'`; company 2's demo clients are `'EN'` to match their English content. Both companies cover every quote/invoice status, every accepted quote with its chantier (completed and invoiced, planned on the calendar, or still to plan) and a 30-day default due date on their document templates. Update this file in the same pass as any schema change it touches — it drifts silently otherwise. `documents.amount_excl_vat`/`amount_incl_vat` here are hand-computed (raw SQL bypasses `recomputeDocumentTotalsServ`) — keep in sync by hand if you touch seeded lines. **`project_types` is global** (no `company_id`) but company 2 needs its own English labels without touching company 1's French ones - its projects reference a separate set of English rows (ids 9-16, see `003_add_english_project_types.sql`) rather than the original French 8; [scripts/reset-demo-company.sql](scripts/reset-demo-company.sql) looks these up by label (a subquery), never by a literal id, since a real user of either company could add a custom type by hand and shift what id a label actually has.
- **Multi-tenant isolation is mandatory on every query touching a single resource by id.** `company_id` is the tenant boundary — any repository function doing `WHERE id = $1` without `AND company_id = $2` (from `req.user.company_id`, never the body) is a cross-tenant leak. This bug existed in nearly every module until audited and fixed — scope new endpoints the same way from the start. List endpoints already filter by `company_id`. Exception: `project_types` is a global lookup table, no `company_id`.
- **Archive instead of delete**: business records (clients, projects, documents, resources) use `is_active` — `PATCH /:id/archive`/`/:id/unarchive`, `GET /` excludes archived unless `?includeArchived=true`. Follow this for new removable entities. `users` keeps a real `DELETE` (account, not business record); so does `project_types` (shared lookup — deleting one nulls `project_type_id` on referencing projects).
- **Errors**: throw from `shared/types/errors.ts` (`NotFoundError`→404, `ConflictError`→409, `UnauthorizedError`→401, or `AppError` directly) instead of plain `Error`. One error middleware at the end of `app.ts` maps them; Express 5 forwards rejected async promises to it automatically, no `try/catch` needed.
- **Roles**: `'ADMIN' | 'USER' | 'PLATFORM_ADMIN'` on the JWT payload, enforced with `requireRole(...roles)` after `authenticate`. `ADMIN` = that company's admin; `USER` = employee (business modules stay open to any authenticated company user, no role check); `PLATFORM_ADMIN` = whole-SaaS, not tied to one company's data.
  - `company_id` on `users` stays `NOT NULL` even for `PLATFORM_ADMIN` — deliberate, see [zz_docs/Decisions.md](zz_docs/Decisions.md).
  - **Cross-company access ("impersonation") — built**: `POST /auth/impersonate/:companyId` (`PLATFORM_ADMIN` only) issues a new access token with that company's own `company_id` swapped in, `role` staying `PLATFORM_ADMIN` — every endpoint's own `req.user.company_id` scoping does the rest for free. The frontend keeps the platform admin's real token in a second `localStorage` slot (`AuthService.impersonateCompany`/`returnToPlatformView`) to switch back without re-authenticating. Deliberately doesn't touch the refresh token at all — an impersonated session is capped at one access token's lifetime (5h); once it expires the frontend asks to pick the company again rather than risk `POST /auth/refresh` silently dropping back to the platform admin's own company.
  - **User management is centralized to `PLATFORM_ADMIN`, not `ADMIN`** — `GET /user`, `DELETE /user/:id`, and `POST /user`'s authenticated "add an employee" branch (`user.service.ts`'s `createUserService`) all require `PLATFORM_ADMIN` now. An ordinary company `ADMIN` no longer manages their own company's users directly — a `PLATFORM_ADMIN` does it by impersonating that company first (deliberate choice, made once impersonation existed as an alternative). **Matters for the demo account** (see README's Live demo): it logs in as a plain `ADMIN`, on purpose, never `PLATFORM_ADMIN` — a recruiter using it never sees `/settings/users`, `/settings/users/new`, `/settings/login-history`, `/settings/companies`, `/settings/errors` or `/settings/uitest`.
  - **No self-service way to create a `PLATFORM_ADMIN`** — inserted by hand in the DB. `POST /user`'s public registration path always forces `role = 'ADMIN'`.
  - `company.routes.ts` has its own ownership checks (comparing `req.user.company_id` to `req.params.id`, so not in the generic role middleware): reading is open to any role of that company, editing needs that company's own `ADMIN` — both also let `PLATFORM_ADMIN` through regardless of company.
  - `POST /user` has no `authenticate` deliberately — it's both public "register a new company" (unauthenticated: takes a `companyName` and creates the company *and* its first `ADMIN` in one transaction - it never takes a `company_id`, so nobody can claim an existing company) and "an authenticated `PLATFORM_ADMIN` adding an employee" (forces `company_id` from the token, role `ADMIN` or `USER` only - never `PLATFORM_ADMIN`). `POST /company` is `PLATFORM_ADMIN` only now; the frontend's registration is the single `POST /user` call. Don't split into two routes — registration has to be reachable with no token.
  - **`login_history`**: every login attempt (successful or not) is recorded (`auth.service.ts`'s `authUserService`, best-effort - a write failure never blocks login itself), readable via `GET /login-history` (`PLATFORM_ADMIN` only, not scoped to one company), filtered server-side by `?user_id=` (the page's user picker, fed by `GET /login-history/users` - every user with at least one attempt). Attempts against an unknown email, and those of a since-deleted user (`user_id` set null), only show unfiltered.
- **Known, deliberately-unfixed gaps** (see `TODO (security)` comments): CORS wide open, Postgres port published to the host (dev compose only), `POST /project-type` open to every company although `project_types` is global (the frontend creates types inline, so it can't just be locked to `PLATFORM_ADMIN` like `DELETE` - needs per-company types), no Content-Security-Policy in nginx (PrimeNG's inline styles need whitelisting first), access/refresh tokens in `localStorage`/cookie without rotation. Don't fix opportunistically — flag instead, they need a deliberate decision. See [zz_docs/Difficulties.md](zz_docs/Difficulties.md) for the 2026-10-22 audit and what it fixed.
- **Ids sent in a request body are checked against the caller's company**, same as ids in the URL: a document's `client_id` and `address_id` (which must also be that client's own), a project's `client_id`, a line's `resource_id`, a resource's `parent_resource_id`. A foreign id is a 404, never a foreign-key error. Do the same for any new body field holding an id.
- **Health check**: `GET /health` (`modules/health`, public on purpose, for the external uptime monitor - see [zz_docs/Deployment.md](zz_docs/Deployment.md)) checks the database and MinIO in parallel, 3s timeout each, one check at a time and its result cached 10s (public route: a flood of calls must not starve the pool), 200 or 503 with `ok`/`error` per check and never an error message. `database.ts` listens for the pool's own `error` event: without it, Postgres dropping an idle connection (a restart, a network blip) crashed the whole API.
- **Error tracking, kept on our own server** (`modules/error-log`, `011_add_error_groups.sql` - deliberately not a third-party service like Sentry, so no data leaves the server): every error ending up a 500 (`app.ts`'s error middleware, `recordServerErrorServ` - best-effort, never awaited, never throws; **a client's own mistake is never recorded**: an `AppError`, a `MulterError` - file too large, 413 - and anything carrying a 4xx `status` - express.json's malformed or oversized body, which runs before any route and whose message quotes the body - are answered as such, otherwise anyone could fill the log and its notifications without an account; an upload's `fileFilter` rejects with an `AppError` 400) and every error a user's browser runs into (`shared/monitoring/error-reporter.ts`, Angular's `ErrorHandler` swapped in by `app.config.ts`, plain `fetch` to `POST /error-log/client` - authenticated, rate-limited, at most 10 distinct reports per page load - i.e. until a reload, it's a SPA - HTTP errors skipped) lands in `error_groups`, **one row per distinct error** with a counter and first/last seen. The grouping key is `error_log.fingerprint.ts`'s `buildFingerprint` (tested): source + type + message with its numbers masked + for a backend error the first stack frame in our own code, function and file without the line (an edit above it would otherwise split an open bug in two); a frontend stack is minified and changes with each build, left out, and a browser group keeps its first stack (a report is user input). Kept: the URL (query string dropped, numeric ids as `:id`), the error's message (which can quote data - a database error quoting a value - so it stays on our server, never sent to Discord), the stack and the last company/user ids. No request body or header. `/settings/errors` (`PLATFORM_ADMIN` only, every company's): open/resolved/all, the stack folds out, "resolved" until the same error comes back (`recordErrorInDB` clears `resolved_at`). **Discord notification** (`shared/notifications/discord.ts`, `DISCORD_WEBHOOK_URL` in `backend/.env` - a secret, unset locally so nothing is sent): only a new error or one back after being resolved (`recordErrorInDB` returns `new`/`reopened`/`repeat`), never a repeat. The message is deliberately minimal - type, browser/server, location and a link to `/settings/errors` (`APP_URL`), **never the error's message** (it can quote data, Discord is a third party) - built by `error_log.notification.ts`'s `buildErrorNotification` (tested; values in code spans with backticks neutralized, `allowed_mentions` off, a browser report being user input). At most 5 a minute, the rest summed up in one message once the minute is over. Fire-and-forget with a 5s timeout.
- **Storage quota**: 500 MB of project attachments per company (`project_attachment.service.ts`, archived files count - their object stays in MinIO), a 413 past that.

## Frontend (`frontend/`)

- Angular 21 + PrimeNG + Tailwind CSS v4. `ng serve` (`npm start`), port 4200.
- Feature modules under `src/app/features/`, shared models/services under `src/app/shared/`. Current: `auth`, `admin`, `clients`, `addresses`, `projects`, `resources`, `documents`, `document-scanner`, `qr-bill`, `calendar`, `dashboard`, `profile`, `settings`, `uitest`.
- API base URL from `environment.ts`/`environment.prod.ts` (swapped at build time via `angular.json`'s `fileReplacements`) — always `environment.apiUrl`, never a hardcoded URL. Dev builds proxy `/api/*` to `localhost:3000` via `ng serve`'s own `proxy.conf.json` (`angular.json`'s `serve.options.proxyConfig`) — same relative-URL pattern prod uses with nginx, so the browser only ever talks to one origin (this is what makes testing through a devtunnel or a LAN IP work at all).
- **Every route in `app.routes.ts` is lazy** (`loadComponent`, not `component:`) — keeps the initial bundle under `angular.json`'s budget (500kB/1MB raw). Follow this for new routes.
- **A chantier's resources open read-only** (`project-resources.ts`), an IN_PROGRESS one included: "Modifier" switches to editing, "Annuler" reloads what's stored, "Enregistrer" saves and goes back to reading. A COMPLETED one has no "Modifier" at all (`locked`).
- **Archive/restore UI pattern** (every list): a signal-backed "Afficher les archivés" `p-checkbox` above the table, row actions show "Archiver"/"Restaurer" per `item.is_active`, confirmed via the shared `ConfirmDialogComponent`. Follow the same shape for a new entity.
- **Role-gated UI**: `AuthService.isAdmin`/`isUser` (computed off the decoded JWT) hide/disable actions the backend would reject anyway (UI gating avoids a confusing error, isn't the real security boundary — that's the backend). `role.guard.ts` gates whole routes the same way.
- **Auth token refresh**: only the access token lives in `localStorage` (`docky_token`) - the refresh token is an httpOnly cookie the browser handles on its own (see Backend), `AuthService` never reads/stores it. `login`/`refresh`/`logout` all pass `withCredentials: true` so the cookie is sent/received. `auth.interceptor.ts` catches a 401 (except on `/auth/login`/`/auth/refresh`), refreshes, retries once; dedupes concurrent 401s into one `/auth/refresh` call. `logout()` also revokes server-side (best-effort).
- **UI text stays French** by default — only code identifiers are English. Not leftover debt, a deliberate convention (see [zz_docs/Decisions.md](zz_docs/Decisions.md)).
- **i18n: Transloco** (started 2026-10-09, see [zz_docs/Decisions.md](zz_docs/Decisions.md) for why over `@angular/localize`) — FR/EN only for now. `public/i18n/fr.json`/`en.json`, one nested namespace per feature (`clients.*`, `projects.resources.*`...), reusing a key across features where the word is identical in both languages rather than duplicating it (e.g. `common.cancel`, `clients.detail`). A string embedding a literal `{{token}}` meant to survive untouched (the PDF placeholders in `documentTemplates.placeholders.*`/`documents.textBlock.placeholdersHint`) is never put through Transloco as part of a translated value - its own interpolation syntax is the same `{{param}}`, so an unrecognized one is silently dropped, not left as-is (see `document-text-block.ts`'s own comment). `AuthService` syncs Transloco's active language to the logged-in user's own `language` (backend, see below) via an effect; `/settings/language` (`p-selectbutton`) lets them change it, `PATCH /user/language`. **Gotcha**: a one-off `transloco.translate()` call inside a `computed()` can run before that language's JSON has finished loading, cache the raw key as a fallback, and never re-run (nothing it reads changes again afterwards) - use `translateSignal()` instead (a real signal, re-evaluates once loading finishes and again on a later language switch), or read `transloco.activeLang()` first inside the `computed` to force a dependency. A value PrimeNG itself renders as plain text (a `p-menu`/`p-select` `optionLabel`, a dynamic `app-list-toolbar` `title`) needs translating before it reaches that component - the `| transloco` pipe only helps where *this* template interpolates the text itself.
- **Account navigation**: `nav-bar`'s bottom item (the user's email) opens a flyout popup - **Paramètres** (→ `/settings`), **Profil** (→ `/profile`), a thin separator, **Déconnexion**. `/profile` is a single page, just the "Mon entreprise" form (`CompanyProfile`). `/settings` (`Settings`, a `p-menu` side layout) lists Modèles de documents (→ `/settings/templates`, `DocumentTemplates`: the Facture/Offre/Rappel tabs + default payment terms), Langue (→ `/settings/language`) and, for `PLATFORM_ADMIN` only, UI Kit/Entreprises/Utilisateurs/Nouvel utilisateur/Historique des connexions/Erreurs. It used to be all under `/profile`.
- **nav-bar is a collapsible icon rail**, not text links: one `pi` icon per page, PrimeIcons, `height: 100vh`, `position: sticky`. A toggle button at the top (`NavBar.expanded`, persisted per-browser in `localStorage` as `docky_nav_expanded`) switches between collapsed (64px, label shown as a hover tooltip) and expanded (224px, label always visible inline - long labels ellipsize via `truncate`, not wrapped). Click on a multi-link item (Documents, Ressources) opens a `<details>` flyout with the sub-links, closed either by clicking a link or anywhere else on the page (`NavBar`'s own `document:click` listener). Fully Tailwind utility classes now (`nav-bar.css` is empty, see the CSS bullet below) - no PrimeNG `p-tooltip`/`p-menu` here though, same reasoning as before: trying those first added ~99kB to the *initial* bundle (nav-bar is eagerly loaded as part of the app shell, and neither was used anywhere else yet, so their whole overlay/positioning machinery landed in the eager bundle). **Gotchas**: `nav` needs its own explicit `z-index` (not just `position: sticky`, which alone leaves it `z-index: auto`) - without one, `nav`'s whole subtree competes against page content purely by DOM order at the outer stacking level, and no amount of z-index on a *descendant* tooltip fixes that. This project has no bridge between PrimeNG's own `--p-surface-*` theme variables and Tailwind (no `tailwindcss-primeui` plugin, no `@theme` block) - a `surface-*` Tailwind class (`text-surface-500` etc.) silently compiles to nothing; use Tailwind's own palette (`gray-*` etc.) instead. And a flex item's default "never shrink below content size" floor is real: an expanded rail item needed both `min-w-0` *and* an explicit `md:w-full` (not just the parent's `items-stretch`, which measured 3px short in practice) to keep a long label from pushing its own hover background/border past nav's own right edge - apply both, at the exact same element, together.
- **On a phone (below Tailwind's `md`, 768px) nav-bar is a fixed bottom bar** instead of the rail: icons only (no toggle, no logo, no labels), flyouts and the account popup open upward, `env(safe-area-inset-bottom)` padding for the iPhone home indicator; `app.css` stacks `.layout` vertically, clips anything wider than the screen (`overflow-x: clip` - one overflowing element widens a phone's layout viewport and pushes the fixed bar off-screen) and pads `.content`'s bottom so nothing hides behind the bar. The breadcrumb (`app-header`) is hidden on phones. FullCalendar's own CSS is unlayered, so it beats Tailwind's utilities - a Tailwind class overriding it needs `!`. The calendar follows the same breakpoint (`BreakpointService.isMobile`, see the next bullet): week list view (`@fullcalendar/list`) with a Liste/Mois switch in the footer, no drag-and-drop, no "Sections à planifier" sidebar, and "+ Note" (next full hour, one hour long) - a p-button above the calendar on desktop, a FullCalendar custom button in its own toolbar on a phone (`customButtonsFor`, buttons shrunk with `max-md:[&_.fc-button]:...!`). On a phone the note form edits start/end as four native `type="date"`/`type="time"` inputs (the iPhone's own wheels - `note-time.ts`, moving the start drags the end along), and a day tapped in the month view starts at 8:00 for an hour. **Gotcha**: a `p-datepicker` inside a `p-dialog` needs `[autofocus]="false"` - PrimeNG's `pAutoFocus` only removes the attribute for an explicit `false`, an unset input renders `autofocus="true"` and the browser opens that picker as soon as the dialog shows.
- **Phone layout (below `md` only - no tablet layout, the app is mainly used on a desktop)**: one breakpoint for the whole app, `shared/services/breakpoint.service.ts`'s `BreakpointService.isMobile` (a root signal off `matchMedia`, `MOBILE_QUERY` = Tailwind's `md`) - anything switching in TypeScript or with `@if` reads it, never its own media query; plain layout tweaks stay `max-md:`/`md:` classes. `shared/ui/mobile.css` holds the global phone rules: every field at 16px (Safari iOS zooms into any smaller one on focus), `.ui-form` fields full width, every `p-dialog` full width whatever its own inline `width`. **Lists turn into cards** on a phone (`@if (isMobile()) { cards } @else { the p-table }` - clients, documents, chantiers, resources, a client's addresses, the dashboard's tables, the admin lists): the key fields, the row's own ⋮ menu, tapping the card opens its detail page where there is one. Deliberately **no inline row editing on a phone** (the pencil's fields, a resource, an address) - accepted as desktop-only; a document's status is the one exception (`document-list.ts`'s `changeStatus`, same save path as the table's cell editor). A document's lines and a chantier's resources are still their desktop table, scrolling sideways - left as is for now. `/settings`'s side menu becomes a row of chips above the page.
- **PWA - installable on a phone's home screen**: `@angular/service-worker` (`provideServiceWorker` in `app.config.ts`, prod builds only - never under `ng serve`), `ngsw-config.json` caches the app shell (JS/CSS/`i18n/*.json`/images) and never touches `/api/**` (no `dataGroups`: data always comes from the network, the app just opens offline). `public/manifest.webmanifest` + `public/icons/` (192/512 + `apple-touch-icon.png` 180, all generated from `zz_brand/docky-icone-vert-sur-blanc.png` on an opaque white background), theme color `#037a3f` (the logo's own green). `frontend/nginx.conf` serves `ngsw-worker.js`, `ngsw.json` and the manifest with `no-cache` (they keep the same name between builds - the one-year immutable rule would freeze an installed app on an old version) and gives the manifest its MIME type, missing from nginx's own `mime.types`. A frontend `nginx.conf` change ships with the frontend image, no gateway restart needed.
- **`app-help-button`** (`shared/components/help-button/`): a reusable "?" icon button - click opens a `p-popover` showing whatever's projected into it via `ng-content`. Unlike nav-bar, safe to use PrimeNG's own overlay (`Popover`) here since this only ever lives inside already-lazy feature pages - its weight lands in that page's own chunk, not the initial bundle.
- **CSS is being phased out in favor of Tailwind + PrimeNG** (see [zz_docs/Decisions.md](zz_docs/Decisions.md)): per-component `.css` files are emptied (not deleted) once a page's layout is redone in Tailwind utility classes directly in the template - `document-form`, `login` and `nav-bar` are done this way so far, several other feature `.css` files are still empty/unconverted. `shared/ui/*.css` stays as genuine global CSS for the cases Tailwind/scoped styles can't reach - a page's own scoped styles can't touch a PrimeNG child component's *internal* markup (different encapsulation boundary), e.g. `select.css` overrides `p-select`'s dropdown option list, which a page-scoped stylesheet can't reach no matter how it's targeted. No comments in CSS files - explanatory ones went in commit messages/here instead.

## Testing

- **Vitest on both sides** (`npm test`). Started 2026-09-02 with unit tests on pure functions only (no DB, no HTTP, nothing async) - that's still all `npm test` runs. Frontend E2E (Playwright...) not without discussing first, see [zz_docs/Decisions.md](zz_docs/Decisions.md).
- **Backend integration tests** (`npm run test:integration`, since 2026-10-30, in `backend/src/integration/`, excluded from `npm test` by `vitest.config.ts`): Supertest against the whole Express app (`app.ts`, no server started) and a real Postgres 17 that Testcontainers starts in Docker for the run (`global-setup.ts`: `000_base.sql` + `001_data.sql`, then the app's own `runMigrationsServ()` through `MIGRATIONS_DIR` - the schema a fresh prod volume gets), thrown away at the end. Needs Docker running (Docker Desktop locally; the CI runner has it). `env.ts` points each test file's process at that database, with test JWT secrets, a dummy S3 (no flow tested stores a file) and no Discord webhook. Each test file makes its own companies and users straight in SQL (`helpers.ts`'s `createCompanyWithAdmin`... - the public registration is rate-limited to 5 an hour) and logs in through `/auth/login` - never relies on the seeded companies or on another file's data. Covers so far: login/refresh/roles (`auth.test.ts`), cross-company access by id (`tenant-isolation.test.ts`), accepting a quote into a chantier, concurrent accepts included (`quote-to-project.test.ts`), saving a document's content - totals, validation, rollback, concurrent saves past the pool's size (`document-content.test.ts`) - and an invoice's lifecycle, numbering and invoicing a chantier once, concurrent creations included (`invoice-lifecycle.test.ts`). A bug fixed on purpose gets a test that fails without the fix.
- Existing coverage: backend `document.calculations.ts` (totals, `lineTotal`), `pdf/templates/placeholders.ts` + `document.placeholders.ts` + `pdf-labels.ts` (placeholders, PDF language and dates), `reminder.placeholders.ts`; frontend `display.ts`, `document-draft.ts`, `document-scan-match.ts`, `api-error.ts`, `note-time.ts`; backend `pdf/templates/format.ts`, `error_log.fingerprint.ts`, `error_log.notification.ts` — each with a colocated `*.test.ts` (plus `app.spec.ts` and a scaffold-style `client-form.spec.ts`). `api-error.test.ts` is the one async exception to "nothing async" (reading a Blob body) - still a pure function, no I/O. Don't assume anything else has coverage. All pass (49 backend unit, 25 backend integration, 53 frontend as of 2026-10-30), and CI (see Deployment) runs all three before deploying. Not covered by an integration test yet: PDFs, file uploads (MinIO), the dashboard, the calendar.
- **Pattern to repeat**: pull the pure calculation out of anything mixing logic with I/O into its own small function/file, test that; the I/O orchestration stays where it was. Don't extract something that secretly still touches I/O.
- Test files: `<name>.test.ts` colocated next to `<name>.ts`.

## Environment / running locally

- Two `.env` files (root for Docker Compose, `backend/.env` for Express) — see README's "Environment variables" table before guessing a variable name.
- Backend + Postgres: `docker compose up --build`. Frontend: `ng serve` separately (no Docker for it yet).
- `backend/Dockerfile` is multi-stage (`dev`/`build`/`prod`); `docker-compose.yml` pins `target: dev` — don't remove it. `prod` (`node:22-slim`, compiled `dist/`, non-root) is what `docker-compose.prod.yml` deploys (see Deployment).
- **On Windows, the dev container's `tsx watch` doesn't always see edits** made on the host through the bind mount - if a backend change seems ignored, `docker restart docky-backend`.
- **After adding a backend dependency**, `docker compose up --build` alone can leave a stale `node_modules` (the anonymous volume that stops the bind mount from shadowing installed deps persists across rebuilds). Run `docker compose down -v` first (also wipes `postgres_data` — harmless, migrations rerun).
