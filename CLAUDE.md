# Docky — Working conventions

Solo learning project (SaaS for small construction companies). See [README.md](README.md) for the full pitch, stack and domain model — this file is about *how to work in this repo*, for Claude and future contributors.

## Workflow

- **Git**: work directly on `main` — no feature branches. Only commit or push when explicitly asked.
- **Push**: never push without an explicit go-ahead, even after committing.
- **Commit messages**: `<Area> : <what changed>` style, e.g. `Backend : scope client lookup by id and delete to the caller's company`, `Frontend : add resource archive/unarchive actions`. Areas seen so far: `Backend`, `Frontend`. English, imperative/present tense, no period at the end. Older history used a lowercase `backend :`/`frontend :` prefix — capitalized is the current convention, use it for new commits.
- One commit per module per side (e.g. a backend change and its matching frontend change are two separate commits) — matches how every multi-file change so far has been split.
- **English is the project's main language, everywhere** — code identifiers, DB tables/columns, doc filenames and content. This is a change from the project's early days, where domain vocabulary and docs were in French (`Entreprise`, `Client`, `Offre`, `Facture`...) — that migration is complete as of 2026-09-02, see [zz_docs/Decisions.md](zz_docs/Decisions.md) for the full French→English glossary and how it was done in phases. **Two things deliberately stay in French, not naming**: the sample data content in `zz_migrations/001_data.sql` (seeded names, Swiss addresses, business text) and the frontend's user-facing text (form labels, buttons, page titles, error/success messages) — both are content shown to a French-speaking Swiss end user, not code.

## Backend (`backend/`)

- Express 5 + TypeScript, run via `tsx watch src/server.ts` (`npm run dev`).
- **No ORM, by design** — raw SQL through `pg`, via a repository layer. Don't introduce an ORM without discussing it first (see [zz_docs/Architecture.md](zz_docs/Architecture.md)).
- Structure is **feature-module based**, not the flat `controllers/`/`services/` layout the README sketches:
  ```
  backend/src/modules/<domain>/<name>.controller.ts
                                <name>.service.ts
                                <name>.repository.ts
                                <name>.routes.ts
                                <name>.types.ts
  ```
  Each module follows `controller → service → repository`. New features should follow this same per-module layout. Current modules: `auth`, `users`, `companies`, `clients` (also holds `address.*`), `suppliers`, `projects` (also holds `project_type.*`), `catalog` (`resource.*`, `resource_supplier_price.*`), `documents` (`document.*`, `document_complete.*`, `document_line.*`).
- Auth: JWT (`jsonwebtoken` + `bcrypt`), guard in `shared/middlewares/auth.middleware.ts`. Rate limiting on `/auth/login` via `shared/middlewares/rate-limit.middleware.ts` (`express-rate-limit`, 20 attempts/15min/IP).
- **Refresh tokens**: `POST /auth/login` returns both an access token (`token`, 5h, signed with `JWT_SECRET`) and a refresh token (`refreshToken`, 7d, signed with a separate `JWT_REFRESH_SECRET`). The refresh token's hash (never the raw value) is stored in the `refresh_tokens` table (`modules/auth/refresh_token.repository.ts`) so it can be revoked — `POST /auth/refresh` exchanges it for a new access token (checks both the JWT signature/expiry *and* that the DB row isn't revoked/expired), `POST /auth/logout` revokes it. It is **not rotated** — the same refresh token stays valid for its full 7 days unless logout revokes it; see [zz_docs/Decisions.md](zz_docs/Decisions.md) for why rotation and httpOnly cookies were turned down for now. `JWT_REFRESH_SECRET` must be set in `backend/.env` (see `.env.example`).
- File uploads via `multer` (see `companies/company.upload.ts`), written to local disk (`backend/uploads/`). **TODO: not production-ready** — local disk works in dev only because `docker-compose.yml`'s `./backend:/app` bind mount happens to persist it to the host; the `prod` Docker stage has no such mount, so uploaded files vanish on every container restart/redeploy there. Needs a decision once a hosting platform is picked: a persistent volume if the host offers one, otherwise move to S3-compatible object storage (Cloudflare R2 suggested — cheap, S3 API, no egress fees) — see [zz_docs/Decisions.md](zz_docs/Decisions.md).
- PDF/invoice generation (incl. Swiss QR-bill) lives under `backend/src/pdf/`.
- **Document numbering is server-generated, not client-supplied.** `POST /document` ignores any `number` in the body — `document.service.ts`'s `generateDocumentNumber` builds it as `{OFF|FAC}-{year}-{4-digit sequence}` (`OFF` for `QUOTE`, `FAC` for `INVOICE` — French, like the seed data and PDF content, since it's printed on the document and shown to the client, not a code identifier), scoped per `company_id` + `type` + current year, backed by `UNIQUE (company_id, number)` on `documents`. The sequence is found via `getLastDocumentNumberFromDB` (a `LIKE 'FAC-2026-%' ORDER BY number DESC LIMIT 1`, which works because the sequence suffix is fixed-width and zero-padded) — not a dedicated counter table, see [zz_docs/Decisions.md](zz_docs/Decisions.md) for why.
- **`document_lines.type` includes two non-priced values**: `SECTION` (a grouping title) and `NOTE` (free text), alongside the priced `MATERIAL`/`SERVICE`. Both have `quantity`/`unit_price` forced to `null` server-side in `document_line.service.ts` regardless of what's sent — there's no `section_id`/hierarchy, a `SECTION` line just visually groups everything after it (in `position` order) up to the next one, same as Odoo's own invoice lines. `computeDocumentTotals` (`document.calculations.ts`) skips any line with a `null` `quantity`/`unit_price` when summing. The invoice PDF (`pdf/templates/dto/invoice.dto.ts`) currently filters these lines out entirely — rendering them in the PDF layout is still TODO.
- **VAT**: `documents.vat_rate` (one rate per document, not per line — Switzerland has a single standard rate) is applied on top of `amount_excl_vat` by `computeDocumentTotals` to get `amount_incl_vat`. **Payment terms**: `documents.payment_terms` (free text) and `documents.due_date` (structured, for future overdue-invoice queries) are separate, complementary columns — set directly on the document, no computation involved.
- **No migration tool yet** — schema is bootstrapped from raw SQL files in [zz_migrations/](zz_migrations/) mounted into Postgres' `docker-entrypoint-initdb.d`. To pick up schema changes, the `postgres_data` Docker volume needs to be dropped and containers restarted (see README's Environment variables section).
- **Seed data**: [zz_migrations/001_data.sql](zz_migrations/001_data.sql) runs automatically right after `000_base.sql` on every fresh `postgres_data` volume (same `docker-entrypoint-initdb.d` mechanism, no separate step) — a full sample dataset (a company, one `ADMIN` login, clients/addresses/projects/suppliers/resources/documents+lines) so there's always something to look at right after a schema reset. **Dev login: `admin@dedonnostyle.ch` / `password123`.** When a schema change adds/renames a column this file uses, it needs updating in the same pass — it drifts silently otherwise (this happened: `suppliers.address` removal and the `documents.status` CHECK broke it until both were fixed here too). The `amount_excl_vat`/`amount_incl_vat` on seeded documents are hand-computed to match their `document_lines` (see the comment in the file) since raw SQL bypasses `recomputeDocumentTotalsServ` — keep them in sync by hand if you touch the seeded lines.
- **Multi-tenant isolation is mandatory on every query that reads/updates/deletes a single resource by id.** This is a multi-company SaaS (`company_id` is the tenant boundary) — any repository function that does `WHERE id = $1` without also filtering `AND company_id = $2` (scoped from `req.user.company_id`, never from the request body) is a cross-tenant data leak. This exact bug existed in nearly every module (clients, suppliers, projects, documents, users, the invoice PDF endpoint) until it was audited and fixed — when adding a new resource or endpoint, scope it the same way from the start. List endpoints (`getXFromDB`) already filter by `company_id` — keep doing that too. Exception: `project_types` is a global lookup table with no `company_id` at all (see below).
- **Archive instead of delete.** Business records (clients, suppliers, projects, documents, resources) use an `is_active BOOLEAN DEFAULT TRUE` column instead of `DELETE` — `PATCH /:id/archive` sets `is_active = false`, `PATCH /:id/unarchive` restores it, and list endpoints (`GET /`) exclude archived rows unless `?includeArchived=true` is passed. A new entity that needs to be removable should follow this pattern, not add a `DELETE` route. `users` still has a real `DELETE` (removing a user account isn't "un-deleting" a business record the same way) — the pattern is for company data, not accounts. `project_types` also uses a real `DELETE` (it's a shared lookup table, not a per-company business record — deleting one nulls out `project_type_id` on any project that referenced it).
- **Errors**: throw a typed error from `shared/types/errors.ts` (`NotFoundError` → 404, `ConflictError` → 409, `UnauthorizedError` → 401, or `AppError` directly for another status) instead of a plain `throw new Error(...)`. A single error-handling middleware at the end of `app.ts` maps `AppError` subclasses to their status code; anything else becomes a generic 500. Express 5 forwards rejected promises from `async` route handlers to it automatically, so controllers/services never need `try/catch` for this.
- **Roles**: `role` is `'ADMIN' | 'USER' | 'PLATFORM_ADMIN'` (`user.types.ts`), on the JWT payload. Enforce with `requireRole(...roles)` (`shared/middlewares/role.middleware.ts`) after `authenticate`, e.g. `router.get("/", authenticate, requireRole("ADMIN"), ...)`. `ADMIN` = that company's admin (staff management, editing company info); `USER` = day-to-day employee (clients/suppliers/projects/documents/resources stay open to any authenticated company user, no role check); `PLATFORM_ADMIN` = manages the whole SaaS, not tied to running any one company's data.
  - **`company_id` on `users` stays `NOT NULL`, deliberately** — a `PLATFORM_ADMIN` account still has a real `company_id` (whichever company it happens to be attached to is irrelevant to its platform-wide access, which is granted by `role`, not by `company_id`). This was a deliberate choice over making the column nullable — see [zz_docs/Decisions.md](zz_docs/Decisions.md) for the trade-off.
  - **There is no self-service way to create a `PLATFORM_ADMIN` account.** It's inserted by hand directly in the database. `POST /user` (registration) forces `role = 'ADMIN'` for its self-registration path — it can never produce a platform admin.
  - `company.routes.ts` has two different ownership rules, both in that file (not in the generic `role.middleware.ts`, since they need to compare `req.user.company_id` to `req.params.id`): reading your own company's info is open to any role of that company (`requireOwnCompanyOrPlatformAdmin`), editing it requires being that company's own `ADMIN` (`requireCompanyAdminOrPlatformAdmin`) — both also let a `PLATFORM_ADMIN` through regardless of company.
  - `POST /user` deliberately has no `authenticate` — it's both the public "register a new company's first admin" flow (see `AuthService.register()` on the frontend: `POST /company` then `POST /user`) and, when a valid token is sent, "an admin adding an employee". `createUserService` tells the two apart: unauthenticated only succeeds if `company_id` has zero existing users (so it can only ever bootstrap a brand-new company) and always forces `role = 'ADMIN'`; authenticated requires `role === 'ADMIN'` on the token and forces `company_id` from the token, ignoring whatever the request body sent for either field. Don't split this into two routes without good reason — the frontend's registration flow depends on this exact endpoint being reachable with no token.
- **Known, deliberately-unfixed gaps** (see the `TODO (security)` comments at each site rather than assuming these are handled): CORS is wide open (`cors()` with no options); the Postgres port is published to the host in `docker-compose.yml`. Don't "fix" these opportunistically mid-task — they need a deliberate decision (see conversation history), flag them instead.

## Frontend (`frontend/`)

- Angular 21 + PrimeNG + Tailwind CSS v4. Run via `ng serve` (`npm start`), port 4200.
- Feature modules live under `src/app/features/`; shared models/services under `src/app/shared/`. Current feature modules: `auth`, `admin` (user list/form), `clients`, `addresses` (the `address.service.ts` used from client/supplier detail pages), `suppliers`, `projects`, `resources`, `documents`, `profile` (company info), `uitest`.
- API base URL comes from `src/environments/environment.ts` (dev) / `environment.prod.ts` (prod), swapped at build time via `angular.json`'s `fileReplacements`. Never hardcode `http://localhost:3000` (or any API URL) in a service — import `environment` and use `environment.apiUrl` instead, like every existing service does.
- **Every route in `app.routes.ts` is lazy-loaded** (`loadComponent: () => import(...)`), not `component: XxxComponent`. This keeps the initial bundle under the `angular.json` budget (500kB warning / 1MB error, checked on raw size) — eagerly importing components in `app.routes.ts` was the actual cause of the initial bundle blowing that budget (1.21MB → 485KB once every route went lazy). New routes should follow the same `loadComponent` pattern by default.
- **Archive/restore UI pattern**, used consistently across every list (clients, suppliers, projects, documents, resources): a `p-checkbox [binary]="true"` "Afficher les archivés" toggle above the table (signal-backed, re-fetches with `includeArchived`), and the row action menu shows "Archiver" or "Restaurer" depending on `item.is_active`, confirmed through the shared `ConfirmDialogComponent` (not the native `confirm()`). Follow this same shape for a new entity's list rather than inventing a new one.
- **Role-gated UI**: `AuthService.isAdmin` / `isUser` (computed signals off the decoded JWT) — use these to hide/disable actions the backend would now reject, e.g. `profile.ts` disables the whole form and hides the save/upload-logo actions for a non-`ADMIN` (backend enforces this too — the UI gating is just to avoid a confusing 403, not the actual security boundary). `role.guard.ts` gates entire routes (`/admin/users*`, `/uitest`) the same way; do the same for a new admin-only page.
- **Auth token refresh**: both tokens live in `localStorage` (`docky_token`, `docky_refresh_token`, set together by `AuthService.login()`). `auth.interceptor.ts` catches a 401 on any request other than `/auth/login`/`/auth/refresh` itself, calls `AuthService.refreshAccessToken()`, and retries the original request once with the new access token — if the refresh itself fails, it logs out and redirects to `/login`. `refreshAccessToken()` dedupes concurrent callers (several 401s at once share one `/auth/refresh` call) via a cached in-flight `Observable`, reset once it settles. `logout()` also POSTs to `/auth/logout` to revoke the refresh token server-side (best-effort — tokens are cleared locally either way).
- **UI text stays French** (form labels, buttons, page titles, success/error messages) — only code identifiers (variable names, `formControlName`, CSS classes, component/service/file names, routes, query params, enum values) are in English. See the language-convention bullet above and [zz_docs/Decisions.md](zz_docs/Decisions.md) for why. Don't "fix" French UI strings into English — that's the deliberate, current convention, not leftover debt.

## Testing

- **Vitest on both sides** — `npm test` (`vitest run`) in `backend/` and in `frontend/`. Started 2026-09-02, Omar's first time writing tests on any project; deliberately started tiny and stayed that way — don't scale this up (a real test DB, Supertest, E2E...) without discussing it first, see [zz_docs/Decisions.md](zz_docs/Decisions.md) for what was considered and explicitly deferred.
- **What exists so far is unit tests on pure functions only** — no database, no HTTP, nothing async: `backend/src/modules/documents/document.calculations.ts` (`computeDocumentTotals`) and `frontend/src/app/shared/utils/display.ts` (`clientDisplayName`, `archiveActionLabel`), each with a colocated `*.test.ts` next to it. Don't assume a service/component/repository has any test coverage just because the module does — most of the codebase doesn't yet. The frontend also has a default Angular CLI smoke test (`app.spec.ts`) that fails on a missing `ActivatedRoute` provider — pre-existing, unrelated to the above, not yet fixed.
- **The pattern to repeat**: when a function mixes real business logic with I/O (a DB call, `HttpClient`, etc.), pull the pure calculation/decision part out into its own small function/file with no I/O — that's what makes it testable without mocking anything. The orchestration (fetch → compute → save) stays where it was and calls the pure function. Don't extract something *into* a pure file unless it's actually free of I/O — half-measures (a "pure" function that secretly still calls the DB) defeat the point.
- Test file naming: `<name>.test.ts` colocated next to `<name>.ts`, not a separate `tests/` tree — matches the project's existing colocate-by-feature convention.

## Environment / running locally

- Two `.env` files (root for Docker Compose vars, `backend/.env` for the Express app) — see README's "Environment variables" table before assuming a variable exists or guessing its name.
- Backend + Postgres run via `docker compose up --build`. Frontend is run separately with `ng serve` (no Docker for it yet).
- `backend/Dockerfile` is multi-stage (`dev` / `build` / `prod`). `docker-compose.yml` pins `target: dev` — that's the one actually used locally, don't remove it or compose would build the last stage (`prod`) by default. The `prod` stage (`node:22-slim`, compiled `dist/`, non-root) is what CI/CD should build for deployment; it hasn't been wired into a pipeline yet.
- **After adding a new backend dependency**, `docker compose up --build` alone can still start the container with a stale `node_modules` — the anonymous volume (`- /app/node_modules` in `docker-compose.yml`, there to stop the `./backend:/app` bind mount from shadowing the image's installed deps) persists across rebuilds and doesn't automatically pick up the new package. Run `docker compose down -v` first (this also wipes the local `postgres_data` volume — harmless for dev data, migrations rerun on next `up`).
